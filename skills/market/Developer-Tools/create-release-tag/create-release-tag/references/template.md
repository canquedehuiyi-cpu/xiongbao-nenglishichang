# 七段式发布说明模板与归纳规则

## 模板结构（固定七段）

```
一、新增功能
二、功能优化
三、缺陷修复
四、配置变更
五、数据库变更
六、注意事项
七、回滚方案
```

无对应内容时对应段落写"无"，各段条目编号 1. 2. 3. 依次排列。

## 归纳规则（提交 → 发布说明的映射）

| 提交类别（前缀/关键词） | 归入段落 | 写法要求 |
|---|---|---|
| `feat` / 新增 / 支持 / 上线 / 接入 | 一、新增功能 | 多条相关提交合并为一条功能级描述，如同一能力拆分的多个提交合并为"XX 功能上线" |
| `refactor` / `perf` / 优化 / 调整 / 改进 | 二、功能优化 | 描述面向用户的价值（如"优化XX判断逻辑"），不写内部实现细节 |
| `fix` / 修复 | 三、缺陷修复 | 说清修复对象（如"修复弱网环境下请求重试异常问题"） |
| config / env / 配置修改 | 四、配置变更 | 说明变更了什么配置 |
| sql / migration / 字典 / 业务规则数据 / 表结构 / DDL | 五、数据库变更 | 提炼出具体变更点：新增枚举/配置数据、表结构变更（可附 ALTER 语句原文） |
| 无法从提交归纳 | 六、注意事项、七、回滚方案 | 生成后请用户补充，不得虚构 |

## 归纳手法要点

1. **同类合并**：同一功能分散在多个提交（含跨提交联调、修 bug 补丁）时，合并成一句话，只保留最终能力描述。
2. **忽略噪声**：剔除无意义的 chore/文档/格式提交，不进入任何段落。
3. **粒度对齐**：一段话解决一个用户可感知的能力点（前半句能力，后半句价值），如"支持批量导入：减少逐条录入的时间成本"；避免罗列内部实现细节。
4. **语言风格**：产品化的陈述句，避免"修改了 xx 文件""调用了 xx 方法"这类代码视角描述。
5. **数据库变更要具体**：新增字段必须附上完整 ALTER 语句；新增枚举/配置数据要说明归属（所属表、用途）。

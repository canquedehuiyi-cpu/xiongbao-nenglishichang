# 按规范创建并推送 Release Tag

## 流程总览

```
Task Progress:
- [ ] Step 1: 选项框一次性询问参数（版本区间起点 + tag 名称）
- [ ] Step 2: 收集区间提交记录
- [ ] Step 3: 整合生成 tag 消息（七段式发布说明）
- [ ] Step 4: 展示完整草案，弹出选项等待确认
- [ ] Step 5: 创建本地 tag
- [ ] Step 6: 弹出选项确认后推送
```

## Step 1：一次性询问参数（每次执行都必须重新询问）

**每次收到「打 tag」或触发本技能的命令，都必须当作全新一轮处理：重新执行一次性询问，收齐本轮参数前不得继续。严禁沿用历史会话中已收集的参数或已生成的草案直接执行创建。**

**弹框前零命令：弹出本次 AskUserQuestion 之前，禁止执行任何 git 命令（包括 git describe/log/rev-parse 等只读预检）**；所有仓库状态查询（最近 tag、候选 tag 是否已存在、HEAD 位置等）一律在用户完成点选后、按所选选项再执行，禁止以「预检/准备选项」为由提前查仓。

**一次性收集全部必要参数，收齐后立即连续执行 Step 2~4 直到产出草案，中间不再插入任何询问。** 参数收集用 AskUserQuestion 一次性弹出（点击选项为主，自由输入通过「Other」填写），需收集的内容：

1. **版本区间起点**（终点默认 = HEAD，需自定义可一并填写）：
   - 点选「上一 tag」→ 自动执行 `git describe --tags --abbrev=0 HEAD` 取最近一次 tag 为起点；
   - 点选「Other」输入 commit hash → 视为自定义起点（格式：`起点..终点` 可同时自定义终点）。
   - 若仓库无 tag（`git describe` 失败），请用户在「Other」中改输起点 commit hash。
2. **tag 名称**：询问本次要创建的完整 tag 名称（不自动加工，用户在「Other」输入，如 `3.10.0`、`V3.0.1`）；随后检查是否已存在：`git tag -l <tag>`，存在则请用户更换。tag 打在区间终点 commit（默认 HEAD）。
3. 其余无法从提交归纳的内容（如 六、注意事项、七、回滚方案）**不要单独提问**，在 Step 4 草案中以「待补充」标记呈现，由用户在确认环节一次性给出。

收齐以上参数后立即进入 Step 2，中途不再提问。

## Step 2：收集区间提交记录

```
git log --no-merges --pretty=format:'%h|%s' <start>..<end>
```

- 过滤 merge 提交；若提交量很大可先按功能模块归类再归纳。
- 保留原始提交列表供归纳参考，不要直接粘贴到发布说明。

## Step 3：整合生成 tag 消息（核心步骤）

按「七段式」结构生成发布说明，模板与归纳规则见 [template.md](references/template.md)，期望风格参考 [example.md](references/example.md)。

归纳要点：

- **一、新增功能**：把 `feat`/新增/支持/上线 类提交合并归纳为**功能级要点**（一条功能一行，多条相关提交合并成一句用户可读描述；同一能力下的多个实体——型号、模块、配置项——合并为一条并逐项列出，如"新增 XX 系列：A 型/B 型/C 型"；必要时括号补充要点说明）。
- **二、功能优化**：`refactor`/`perf`/优化/调整/选配 类提交同理归纳。
- **三、缺陷修复**：`fix`/修复 类提交归纳，说清修复对象并可附根因（如"修复 XX 问题：因…导致…"）；无则写"无"。
- **四、配置变更**：涉及 config/env/配置 的提交；无则写"无"。
- **五、数据库变更**：涉及 sql/migration/字典/业务规则数据/表结构 的提交，提炼 DDL/DML 摘要；无则写"无"。
- **六、注意事项**：提交记录通常无法体现，生成后**请用户补充**（如环境差异、迁移要点）。
- **七、回滚方案**：请用户补充；团队有固定方案（如发布平台版本记录回滚）时可给出默认文案供确认。
- 无对应内容的段落一律写"无"，不得虚构；空模板段落要引导用户补充。

**发布说明末尾不附加独立的【提交日志】段落**：区间内每个提交都应被归纳进七段式对应段落（新增→一、新增功能；优化/调整→二、功能优化；修复→三、缺陷修复；无对应内容写"无"），避免重复赘余。

**细节保真（重要）**：输出内容必须保留当次提交中的真实业务细节——具体型号/设备/模块名称逐项列出、表名与 ALTER 语句保留原文、缺陷写清对象与根因、上线实体清单完整。references 中的示例仅示范段落结构与句式，**禁止把提交中的真实细节替换、省略或改写成示例的通用措辞**。

**质量要求**：表述精炼、面向用户，整合同类提交而非逐条复制 commit 噪声；细节丰富与行文简洁两者兼得。

## Step 4：展示完整草案，弹出选项等待确认

- 以「**标签名称 + 消息全文**」形式一次展示完整草案（消息为一段完整文本，不是文件路径）：tag 名称、区间（start..end，N 个提交）、七段式发布说明（六、注意事项与七、回滚方案等以「待补充」标出），不分段询问。发布说明中不含独立提交日志；区间原始提交清单仅作核对参考，不写入 tag 消息。
- 草案展示后**用 AskUserQuestion 弹出确认选项**（不要引导用户回复文字）：
  - 「确认创建」→ 立即进入 Step 5 创建本地 tag；
  - 「补充后确认」→ 用户在「Other」一次性给出六、注意事项与七、回滚方案等任意段落的补充内容，按修改后的草案重新展示并再次弹出选项确认；
  - 「暂不创建」→ 直接收尾，不创建 tag。
- **必须通过选项取得用户明确确认后才可创建 tag。**

## Step 5：创建本地 tag

1. 将用户最终确认的**消息全文文本**写入临时文件（用 Write 工具，例如 `.git/release-msg-<tag>.txt`，放在 .git 内不会污染工作区），避免多行/特殊字符的 shell 转义问题。
2. 创建注解 tag：
   `git tag -a <tag> -F .git/release-msg-<tag>.txt <endCommit>`
3. 校验：`git tag -l <tag>`（必要时 `git tag -n1 <tag>` 查看消息）。
4. **创建成功后删除临时消息文件**：删除 `.git/release-msg-<tag>.txt`，避免遗留（tag 对象已完整保存消息全文，删除文件不影响 tag）。

## Step 6：推送（弹出选项确认）

- 本地 tag 创建完成后，**用 AskUserQuestion 弹出推送选项**（不要引导用户回复文字）：
  - 「立即推送」→ 执行 `git push origin <tag>`（仅推送新建的 tag），推送后校验：`git ls-remote --tags origin <tag>`；
  - 「暂不推送」→ 直接收尾，保留本地 tag，提醒用户后续可自行 `git push origin <tag>`。

## 边界与红线

- 未经用户确认不创建 tag、不推送；确认与推送决定一律通过 AskUserQuestion 弹出选项取得（点选/Other 输入），不得把默认推断或闲聊当作确认。
- 绝不执行 commit、merge、reset 等其他 git 写操作。
- 多行 tag 消息一律通过临时文件 `-F` 方式写入，禁止直接拼命令行。
- 发布说明基于当次区间提交重新整合生成，禁止套用历史版本内容；示例仅供理解期望风格。

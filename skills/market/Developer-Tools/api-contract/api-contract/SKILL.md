# API 契约文档生成

为 salt 后端接口生成联调契约 markdown 文档，供前端直连对接使用。

## 唯一产物

本 skill 的最终交付物**只有一份 markdown 契约文档**（`{模块英文标识}-contract.md`），自包含、可直接发给前端对接。除该文档外：不修改任何其他文件、不生成临时笔记/报告、不提交 git。过程中的核对与确认通过对话完成，结论只落入这份文档。

## 硬纪律（防扩散，违反即推倒重来）

1. **清单是范围的唯一来源**：只生成用户提供的接口清单总表内的接口。清单里没有的接口一律不生成——即使前端页面"看起来需要"，也只在文档末尾「缺口提示」中列出，交由后端补清单。
2. **代码为准**：字段名、类型、必填性、枚举值、默认值、校验规则、错误码，必须来自后端实际代码（Controller / DTO / 枚举类 / 校验注解）或后端确认过的对接明细文件，禁止凭推测或常识脑补。
3. **枚举必须全量**：出现"例如 / 如 B1_MISSING…"式不完全枚举即为不合格，必须从代码中列全量；确实动态扩展的写"当前全量值 + 扩展方式"。
4. **不确定就标 `【待确认】`**：留空并汇总到文档末尾「待确认清单」，不得用推测值填空。
5. 后端未实现的接口（清单中标"开发中"）不出契约正文，只保留在清单表。

## 工作流

### 第 1 步：确认输入

- 读入用户给的清单/明细文件（如 `U02 批次查询接口前后端对接明细.md`）。
- 若提供了后端代码仓库路径：用 Grep/Glob 定位对应 Controller 与 DTO，逐字段核对明细与代码，以代码为准修正。
- 若未提供：仅以明细文件为准生成，凡明细中缺失的项（失败响应、错误码、全量枚举）标 `【待确认】`。
- 检查**依赖闭环**：接口 A 入参引用接口 B 出参（如 `fileIds` 取自通用上传接口）而 B 不在清单中 → 记入「缺口提示」。
- 清单有歧义或矛盾时先向用户确认，再动手。

### 第 2 步：全局声明（文档开头）

按 `references/contract-template.md` 的文档骨架，先确定模块级声明：

- envelope：**已定稿为 `ApiResponse<T>`**（2026-09-17，见 `references/spec.md` §2.3）——成功 `{success:true, data, error:null, traceId, timestamp}`，失败 `{success:false, data:null, error:{code,message,details}, traceId, timestamp}`。按此校验后端明细/代码是否一致，有偏差记入「待确认清单」，不得沿用明细中的旧式 `{success:false, errorCode, message}` 失败形态。
- HTTP 状态语义化：200/201 成功；400/401/403/404/409/422/500 按语义；204 无响应体仅限 void 接口。逐接口在正文中标注实际的失败 HTTP 状态。
- 错误码：语义化字符串置于 `error.code`（如 `VALIDATION_FAILED`），HTTP 状态语义化；前端只按 `success` 与 `error.code` 分支，禁止依赖 message 文案。
- mock 接口例外：仍用 `{code:'00000', message, data}`，契约文档不涉及 mock。
- 可空语义：null 还是键省略（逐模块声明）。
- 时间格式、金额格式（string 两位小数）、ID 序列化（雪花 ID → string）。
- `{{baseUrl}}` 各环境取值表。
- 401 行为：空 body，前端刷新重放；`A0230` 为 mock 保留码。

### 第 3 步：逐接口生成

严格按 `references/contract-template.md` 中「单接口模板」输出，每个接口一节，缺项视为未完成：

- 完整 HTTP 请求报文示例（含 Authorization / Idempotency-Key 等 header）
- 请求字段表（位置/字段/类型/必填/含义）
- 响应示例：**成功与失败各一份**（失败示例缺失是历史最大缺口，宁可标 `【待确认】` 也不省略该小节）
- 响应字段表（类型/可空性/中文注释，注释含枚举全量、默认值与非法值处理、防混淆注记、口径说明）
- 错误码表
- 备注（异步轮询、状态机约束、上线计划）

注释写法要求（沿用 U02 明细的优秀实践）：

- 防混淆：易错字段写"不是什么"（"`batchId` 来自 `list[].id`，不是 batchNo"）。
- 语义边界："省略 = 未计价，不等同于 0 元"、"去重后的授权数，不是影响的数据行数"。
- 引用关系：ID 来源写清来自哪个接口的哪个字段。

### 第 4 步：输出与自查

- 输出路径：`docs/api-contracts/{模块英文标识}-contract.md`（用户指定路径则从其指定）。
- 自查清单，全部通过才算完成：
  - [ ] 文档内每个接口都在用户清单中
  - [ ] 用户清单中"已就绪"接口每个都有正文，无遗漏
  - [ ] 无推测字段/枚举/错误码；不确定项全部标 `【待确认】` 并汇总
  - [ ] 枚举全量，无"例如"式写法
  - [ ] 每个接口有失败响应小节（哪怕是待确认占位）
  - [ ] 依赖闭环缺口与待确认项已汇总到文末
- 向用户汇报（对话中简述即可，不落盘）：生成了哪些接口、标记了哪些待确认项、发现哪些清单缺口。

## Resources

- `references/contract-template.md` — 生成文档的骨架与单接口模板（含全局声明、清单表、字段表列定义），生成时严格套用
- `references/spec.md` — 契约规范**自包含快照**（模板与指令中"规范 §N"均指此文件的章节）。本 skill 不依赖仓库内任何文档，可直接分发给后端同学使用；仓库侧 `docs/api-contract-for-backend.md` 更新时需同步本快照

# 进度看板（progress-board）

针对的痛点：**任务一大就抓不住主线，偶尔插一条支线、支线也很长，收不回来，不知道到哪一步了。**
解法：一页 HTML 常驻在项目里，每轮推进后由 agent 更新；用户打开就等于对齐。

## 一、什么时候用

1. **用户点名**：说"创建任务看板 / 建个进度看板 / 加个面板"→ 直接做，别反问一堆。
2. **主动提议**（只提议一次，被拒不再提）：任务跨多轮、插了非主线支线、或攒出 ≥3 个待用户拍板的事项。
3. **看板已存在**：每轮推进后**必须**更新它，这是本技能的主要用法，不需要用户提醒。

## 二、看板是从哪里"转化"来的（先搞清楚输入）

它**不是**新写一份计划，而是把已有事实重排成对外视图。数据来源按优先级：

| 输入 | 能直接转成看板的哪一段 | 缺了怎么办 |
|---|---|---|
| **spec / 施工单**（逐卡：位置·动作·验收·回滚点） | "当前阶段卡清单"、"验收靠什么" | 见下面第三节，先补 spec 或出 v0 草稿 |
| **提交历史**（`git log --oneline`） | "已交付"表：卡号、提交号、可回溯性 | 未提交的工作一律标"未落库"，不许写提交号 |
| **方案文档 / 阶段划分** | 顶部"阶段轨"（P0…Pn 与当前指针） | 只有一句话目标时，阶段轨就写"目标 / 进行中 / 待做"三段，别编期号 |
| **实测与验证记录**（日志、脚本输出、单测数） | 每条的"验到什么程度" | 没测过就写"未验"，禁止推测 |
| **对话里的约束与红线** | "约束与红线"段 | 不确定就不写 |

**硬规则：没了解过项目就凭空生成 = 编造。** 陌生项目走"只读摸底"再出板：读 `README`/`AGENTS.md`/`docs/`、
跑 `git log --oneline -30`、看目录规模，然后才落笔。摸底读不到的字段一律留 `[待填]` 并**显式告诉用户哪些还是空的**。

## 三、要不要先生成 spec？

不必，但两者关系要说清：**spec 是施工图（怎么干、怎么验、怎么回滚），看板是仪表盘（在哪、下一步、什么在等你）。**
按项目当前有没有 spec 分三种情况：

- **有 spec** → 直接转化，卡号沿用 spec 的编号，不要另起一套号。
- **有方案/需求但没拆卡** → 先出一版**能确定的部分**（阶段轨、已交付、待拍、未验），卡清单那节标
  "未拆卡"；然后问用户一句：*"要我先把施工单拆出来，还是先按现在这版看板推进？"*
- **刚起步、什么都没读过** → 先只读摸底，出 **v0 草稿**，然后摆三问定稿：①放哪（默认 `docs/进度看板.html`）
  ②要不要进 git（默认进）③粒度（要不要细到单张卡）。**不要为了"完整"先追问半天**——
  多数用户更愿意先看到能看的东西再迭代，而不是一连串前置问题。

## 四、六段固定结构

模板见 `assets/template.html`（含全部样式，直接复制改内容，不要自己另写 CSS）。

1. **抬头**：项目名、主线一句话、更新时间、`当前` 那一行（全页最重要的一行，必须一眼看到）。
2. **数字条**：4 个关键数（提交数／已交付卡数／待用户拍板数／未验数）。数字必须可核。
3. **阶段轨**：竖排，已完成=绿、当前=蓝带描边、未来=灰。**主线只有一条**，支线不进这条轨。
4. **卡清单**：每条一张 `.item` 卡——卡号 + 名称 + 状态；正文一句"做什么"；`.why` 一句"验收靠什么"。
5. **等你拍板**（`.ask`）：**必须编号**（D1/D2/Q3…），每条含"影响哪一步"，并把推荐的那个用 `<em>` 标出来，
   让用户能"1 按 A、2 不做、3 按推荐"一轮答完。
6. **临时件债务** + **还没验，别当成已验** + **约束与红线**：三段各管一件事——加过的临时东西要列删除清单；
   没验的单独成段；红线（隐私、环境限制、不可承诺的事）逐条写。

## 五、设计规范（窄栏优先）

默认按**窄栏**设计：这类看板通常在 IDE 侧边栏的内置浏览器里阅读，可用宽度常见只有 400–520px。
即使项目主要在宽屏上看，也沿用这套窄栏版式，不要为宽屏改成横向表格——单列在宽屏同样可读，反之不行。

- 单列，`max-width:760px` 居中；**不用横向表格**（窄栏会挤成一竖条），用条目卡 + 左侧 3px 色条表达状态。
- 阶段条用**竖轨**不用横排格子；数字条用 `flex-wrap`，窄栏自动两行。
- 色板克制：纸灰底 `#f1f2f2`、白卡、1px 细线、钢蓝强调 `#1f4e79`；状态色只三档——
  完成/已验 `#2f6f4f`、待拍/部分验 `#8a6210`、未验/缺口 `#8f3232`。
- **禁止**：圆角、渐变、阴影、彩色胶囊标签、emoji、英文副标题。等宽字体只用于卡号与代码。
- 状态词要让不熟悉项目的人一眼懂："真机已验 / 只有单测 / 未开工"，不要写 "verified"、"WIP"。
- 打印友好（`@media print` 已有）。

## 六、每轮怎么更新

改四处就够，别整页重写：`当前` 行、数字条四个数、更新时间戳、把做完的条目移进"已交付"并补提交号。
状态变化要跟着改色条。新出现的待拍事项**追加编号**，不要重排已有编号（用户可能正在按编号回答）。

## 七、红线

- 数字要么实测、要么带 `文件:行号` 出处；错了单独成段更正，不要悄悄改。
- 不许把"编译通过"写成"已验证"；不许把未验事项省掉。
- 看板进 git 或对外发布前确认不含敏感数据（客户机数据库、身份证/姓名、密钥、内网地址、未公开的业务指标）。
- 它是**视图不是事实源**：与 spec 冲突时以 spec 为准，并当场指出冲突，不要两边各写一套。
- 收尾时提醒用户：看板可以留着当交接页，但临时件债务那一段必须清零。

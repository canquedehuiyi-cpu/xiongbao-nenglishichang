# 长上下文与上下文管理

> 用途：处理长文档、多来源材料、超大上下文时的提示词策略；以及在受限窗口（context budget）内的工作流。选型信号：输入超过单次窗口 / 需多窗口接力 / 长文档问答。

## 1. 长上下文的基础策略

- **文档置顶**：最重要的指令/问题放在提示词开头（模型对开头注意力更强）。
- **query 末尾提升**：把核心问题放在文档**之后、提示词末尾**，官方实测"查询放在末尾可提升回答质量至多约 30%（尤其复杂多文档输入）"。做法：`<documents>...</documents><query>你的问题</query>`。
- **引用接地（quote before answer）**：要求模型"先引用原文再作答"（quote the relevant text before answering），显著降低幻觉，便于核验。
- **分块检索**：文档超长时，先分块，只把相关块放进上下文（对应 RAG 模板）。

**推荐结构**

```text
<documents>
（全部或相关文档原文）
</documents>
<query>
（核心问题，放末尾）
</query>
要求：先引用相关原文，再给出结论。
```

## 2. 中间迷失（lost-in-the-middle）

当上下文很长时，模型对**中间段落**的注意力下降。对策：
- 关键事实放开头或末尾。
- 需要"多处原文对比"时，明确要求"逐条引用定位"，而不是让模型自由总结。

## 3. Multi-Context Window 工作流（受限窗口）

当任务超出单次窗口，用多窗口接力，而不是硬塞：

1. **首窗口搭框架**：第一轮只做"读目录/拆解任务"，产出任务结构，不试图一次读完。
2. **跨窗口追踪**：用任务清单（todo）或 git 提交记录，把"已完成/待做"状态持久化，跨窗口恢复。
3. **压缩管理**：每轮结束把已完成内容压缩成摘要（本 skill 用 `compress-verify.mjs` 保分压缩），下一轮只带摘要 + 新任务段。
4. **隔离调试**：失败时只在出错窗口内重试，不重跑全链路。

## 4. 压缩策略（与本 skill 压缩引擎联动）

- 压缩目标：在"保信息"与"省 token"之间取平衡，压缩后**分数不降**才保留（compress-verify 的回归门禁）。
- 压缩对象：背景材料、历史对话、已完成论证；**不压缩**核心问题、约束与验收标准。
- 压缩后保留可回溯锚点（原文位置/版本号），需要时可回滚查证。

## 5. Token 预算意识

- 用 `token-count.mjs` 估算输入输出，明确窗口上限与预留输出空间。
- 输出占比通常需预留 20-30%，避免长输出被截断。
- 超长材料用"摘要 + 全文链接/路径"替代全文灌入。

## 6. 反例（不要这样用）

- 把 10 万字全文硬塞进一次调用 → 中间迷失 + 超窗口截断。
- 核心问题放中间 → 注意力稀释。
- 要求模型总结但不给引用要求 → 幻觉风险高。

## 7. 与其它模块联动

- 模板：RAG.md（检索问答）、SYNTHESIS.md（多源综合）与本文件策略一致。
- 引擎：`compress-verify.mjs`（保分压缩）、`token-count.mjs`（预算）、`search-cache.mjs`（检索缓存）。
- 任务链：超长任务优先走 prompt-chaining.md 拆链，而非硬撑单次上下文。

# 推理模型 vs 非推理模型：提示词差异

> 用途：判断目标模型是"推理型"还是"非推理型"，并据此选择提示词写法。选型信号：目标模型族 = o 系 / Claude Extended Thinking / DeepSeek-R1 / Kimi K2 等推理模型。

## 1. 什么是推理模型

推理模型在生成最终答案前**内部进行长链推理**（对用户不可见的"思考"）。它们擅长数学、逻辑、代码、复杂规划；代价是更慢、更高延迟。

## 2. 核心差异对照

| 维度 | 推理模型 | 非推理模型 |
|------|----------|------------|
| 推理过程 | 内部隐藏，无需用户提示 | 需显式 CoT 或拆步指令 |
| 提示词长度 | 简短更优，废话干扰 | 可适当详细 |
| CoT 指令 | **禁用**（画蛇添足） | 有效（见 techniques.md CoT） |
| 失败时 | 给模型更多"思考预算"（如 Claude min_budget 调大） | 重写指令、加示例 |
| 适用任务 | 数学/代码/逻辑/长链规划 | 事实问答/创作/格式任务/对话 |

## 3. 推理模型的正确提示词写法

1. **简单直接**：把问题说清楚即可，不要教它"怎么思考"。
2. **明确成功标准**：告诉它什么算"做对了"（验收条件），让它自己规划路径。
3. **不强制可见 CoT**：不要要求"请逐步输出思考过程"——推理模型的内部推理已存在，强求可见过程既慢又烧 token。
4. **给"思考预算"而非"思考指令"**：任务难时，在支持的平台上调高思考预算（如 Claude min_budget_tokens），而不是在提示词里反复催"多想一点"。
5. **提供参考/边界**：给足任务背景与约束，剩下的推理交给模型。

**示例**

```text
❌ 非推理式写法（对推理模型是噪声）：
请你一步一步地思考，先列步骤，再逐步计算，每一步都写出来……

✅ 推理式写法：
计算以下表达式的值，要求：结果正确、给出最终答案单独成段。
表达式：{...}
```

## 4. 非推理模型的正确提示词写法

沿用通用技法：清晰的指令 + 适当 CoT（复杂推理时）+ 示例锚定 + 明确的输出格式。

## 5. 何时用哪种模型（提示词设计视角）

- 任务含**严格数学/逻辑正确性**、**长链多条件决策** → 选推理模型，提示词走"简单直接 + 成功标准"。
- 任务含**创作、语气、格式稳定、低成本高吞吐** → 选非推理模型，提示词走完整契约。
- 混合任务（既有推理又有创作）→ 用 prompt-chaining.md 拆链：推理段用推理模型，创作段用非推理模型。

## 6. 反例（不要这样用）

- 对推理模型叠显式 CoT → 冗余、干扰（techniques.md 禁用清单）。
- 对推理模型写超长指令 → 模型把精力浪费在"理解指令"而非"解决问题"。
- 把推理模型当格式工具 → 杀鸡用牛刀，延迟高成本高。

## 7. 与其它模块联动

- 模板：COT.md 头部已标注"o 系禁用"，与本文一致。
- 构建引擎：`build-prompt.mjs` 按 model_family 切换方言，推理族走精简直述方言。
- 自进化：用户反馈中"模型好像没好好思考"类问题 → 先查是不是把推理模型当非推理模型写。

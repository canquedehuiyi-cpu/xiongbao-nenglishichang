# 平台规范实时核实协议

> **定位**：本文件是全 Skill 平台规则的「实时核实强制门（Gate）」。任何涉及平台规则、AI 使用比例口径、AI 声明义务、不符合要求时的处理方式、投稿与签约规范的输出，必须先按本协议联网核实，再交付。本地参数库（`platform-data-registry.md`、`ai-compliance-redlines.md`）只作为基线快照，权威值永远以实时核实结果为准。
> 版本：1.7.0 ｜ 类型：纯指令协议，由对话内执行，不依赖任何脚本或外部程序。

## 一、强制门原则

1. **先核实、后交付**：命中触发条件时，未完成核实不得直接引用本地参数作答。
2. **权威值唯一**：同一规则若实时结果与本地快照冲突，以 L1 平台官方实时结果为准，并回写本地参数库。
3. **来源可追溯**：每条被引用的平台规则必须能给出「来源级别 + 来源链接 + 核实日期」。
4. **不静默用旧值**：无法完成实时核实时，只能以「基线快照 + 快照日期 + 待核实提示」形式呈现，禁止把旧值包装成最新结论。
5. **不编造**：核实不到的规则写「未查到公开口径，以平台后台/官方说明为准」，绝不臆造阈值、比例、日期或处理条款。

## 二、触发机制

### 2.1 硬触发（立即核实，禁止直接引用本地值）

用户请求同时包含「平台名」与下列任一类关键词时，立即进入核实流程：

- 红线类：AI 红线、能不能用 AI、占比多少、AI 比例、算不算代写
- 声明类：要不要标、AI 声明、AI 说明、如实标注、披露
- 处理方式类：会不会封、下架、拒签、限流、扣稿费、平台会怎么处理
- 规范类：投稿规范、签约条件、签约门槛、审核标准、字数要求、分成、全勤

### 2.2 软触发（交付前默认带一轮）

下列交付环节在产出前默认进行一次核实，命中硬触发关键词时升级为硬触发：

- 签约建议、投稿检查、平台适配方案
- AI 声明文案生成（`ai-disclosure-writer.md`）
- AI 占比自测结果对照平台红线（`ai-ratio-tester.md`）
- 市场雷达与爆款对标（`market-radar.md`）
- 跨平台/海外平台合规判断

### 2.3 周期刷新

本地每条参数内置 `verified_date` 与 `ttl_days`。超过保鲜期未核实的条目标记为 `stale`，一旦被引用即触发刷新；未刷新成功前按第八节降级处理。

## 三、核实操作流程

```

第 1 步 · 锁定对象   明确：平台 + 规则类型（占比/声明/处理方式/投稿/分成）+ 交付用途
第 2 步 · 检索官方   优先检索第五节白名单中的 L1 官方来源；检索词用「平台名 + 规则关键词 + 公告/规范/帮助」
第 3 步 · 交叉比对   L1 不足时用 L2 交叉验证；L3 仅作线索，不作为权威值
第 4 步 · 判定变化   与本地快照比对：一致→标记 verified；不一致→以实时为准并记录 changed_from_last
第 5 步 · 回写快照   新值按第七节 FIFO 规则写入本地参数库，旧值进入变更日志
第 6 步 · 带来源交付 输出中附「来源级别 + 链接 + 核实日期」，关键建议提示以平台后台为最终依据

```

### 检索动作要点

- 一次只核一个平台的一类规则，避免多平台口径混淆。
- 检索词优先使用平台正式名称与规则正式表述，例如「起点 AI 辅助创作 规则」「番茄 低质内容 标准」「微信公众平台 AI 创作 声明」「KDP AI content disclosure」。
- 官方页面存在多版本时，以发布时间最新、且仍在适用的版本为准。
- 检索到的数值、日期、条款必须能在来源正文中定位到原文，定位不到则不予采信。

## 四、来源分级与采信规则

| 级别 | 定义 | 典型来源 | 采信处理 |
|------|------|----------|----------|
| L1 官方 | 平台官方公告、作家专区/作者后台规范页、官方帮助中心 | 起点作家专区、番茄作家专区、晋江公告区、微信运营规范、KDP Help | 直接采信为权威值，写入参数库 |
| L2 半官方 | 平台官方账号发声、正规媒体对官方内容的引用与报道 | 正规新闻媒体引述平台公告 | 与 L1 交叉验证后采信，标注来源与媒体名 |
| L3 社区 | 作者社区转述、自媒体测评、无来源截图、论坛讨论 | 贴吧、知乎、短视频转述 | 仅作线索参考，不采信为权威值，不写入参数库 |

采信优先级：**L1 ＞ L2（须交叉验证）＞ L3（仅线索）**。同级来源相互矛盾时，以发布时间更新者为准，并在输出中显式标注存在口径差异。

## 六、平台参数结构（schema）

本地参数库每条规则按下列结构登记，字段缺失视为未完成核实：

```json

{
  "platform": "qidian",
  "rule_type": "ai_ratio_redline",
  "baseline_value": "以平台实时口径为准",
  "obligation": "disclosure_optional",
  "penalty_tiers": ["warn", "delist", "ban"],
  "source_url": "官方来源链接",
  "source_level": "L1",
  "verified_date": "YYYY-MM-DD",
  "ttl_days": 7,
  "cache_policy": "fifo",
  "status": "verified | stale | pending",
  "changed_from_last": false
}

```

字段说明：

- `rule_type`：规则类型，取值 `ai_ratio_redline`（比例红线）/ `ai_disclosure`（声明义务）/ `penalty`（处理方式）/ `submission`（投稿签约）/ `quota`（字数体量）/ `revenue`（分成全勤）。
- `status`：`verified` 已在保鲜期内核实；`stale` 超期待刷新；`pending` 正在核实或尚未取得权威值。
- `changed_from_last`：本次核实相对上一条快照是否发生变化，变化时必须同步写第九节变更日志。

## 七、缓存生命周期：新进旧出与差异化保鲜

### 7.1 新进旧出（FIFO）

- 同一平台、同一 `rule_type` 只保留**最新一条**已核实结果。
- 新值进入时，旧值从「当前值」位移出，转记到第九节规则变更日志（保留旧值用于变化比对），不再参与任何交付引用。
- 不并排放置多个时期的「当前值」，避免新旧口径并存造成误引。

### 7.2 平台差异化保鲜（TTL，不搞一刀切）

按平台规则更新活跃度设置差异化保鲜期，各平台分别计时：

| 保鲜档 | 平台 | ttl_days |
|--------|------|----------|
| 高频（7 天） | 起点、番茄、微信公众平台 | 7 |
| 中频（14 天） | 晋江、七猫、纵横 | 14 |
| 低频（30 天） | Amazon KDP、Wattpad、Webnovel 等海外平台 | 30 |

- 某平台发布重大新规时，不受 TTL 限制，立即对该平台相关条目做一次全量刷新。
- 差异化计时只影响「何时需要重新核实」，不影响采信级别；任何平台的权威值仍以 L1 实时结果为准。

## 八、降级与冲突处理

### 8.1 联网不可用（断网/检索失败）

输出格式固定为：

> 以下为基线快照（查证日：YYYY-MM-DD），尚未完成本次实时核实，**请以平台最新官方说明/作者后台为准**。

禁止行为：不得省略快照日期、不得把快照说成「最新要求」、不得用模型记忆补齐缺失数值。

### 8.2 来源冲突

- L1 与 L2/L3 冲突：一律以 L1 为准。
- 两个 L1 冲突（如新老公告交替）：以适用时间最新者为准，并提示存在过渡期。
- 无法判定谁更新：并列呈现两条口径与各自发布时间，不下单一结论，提示以平台后台为准。

### 8.3 核实不到公开口径

输出「该平台未查询到公开的量化/成文口径，以下为行业通用做法，最终以平台作者后台与签约编辑答复为准」，并把该条目标记为 `pending`。

## 九、规则变更日志

任一参数发生变化，按下列格式追加一条记录（由 `evolution-protocol.md` 统一归档维护）：

```

## YYYY-MM-DD 规则变更记录
| 日期 | 平台 | 规则类型 | 变更点 | 旧值 → 新值 | 来源级别 | 影响模块 | 修订动作 |

```

- 「影响模块」列出需要同步口径的下游文件（如 `ai-compliance-redlines.md`、`platform-guide.md`、`ai-disclosure-writer.md`）。
- 「修订动作」记录是否已回写参数库、是否已通知下游引用更新。
- 日志只记录真实核实到的变化，不记录推测性变化。

## 十、交付前核实清单

每次涉及平台规则的交付，逐项确认：

- [ ] 是否判定了硬触发/软触发，并完成对应核实动作？
- [ ] 每条平台规则是否带来源级别、链接、核实日期？
- [ ] 引用值是否在该平台 TTL 保鲜期内？超期是否已刷新或显式降级？
- [ ] 是否做到同一条目只保留最新值（FIFO），旧值是否已进变更日志？
- [ ] 联网失败时是否按快照 + 日期 + 待核实提示降级，未静默用旧值？
- [ ] 是否存在查不到却被写成确定结论的数值/条款？若有，改为 pending 表述。
- [ ] 关键决策（签约/上架/声明/分成）是否提示「以平台后台实时信息为最终依据」？

### 自检标准（可验证）

1. 对起点、番茄、微信各取一条规则，能跑通「检索 → 比对 → 标注来源与日期 → 回写」全流程。
2. 模拟断网时，输出必须带快照日期与待核实提示，不出现无来源的确定值。
3. 对同一平台连续两次核实，当前值只保留最新一条，旧值只存在于变更日志。
4. 三档 TTL 平台分别按 7/14/30 天计时，互不影响。
5. L3 来源内容不出现在任何「当前权威值」中。

# 红蓝对抗审稿

> **定位**：最高强度的对抗式审稿。红方无差别挑刺，蓝方逐条决策，双方终局收敛为可执行修订清单。目标是在交付前把问题暴露干净，而不是给出让作者舒服的评价。

## 一、审稿口径

红方审稿遵循以下口径（全库统一）：

1. **直接客观、实话实说**：问题是什么就说什么，不挑好听的讲，不顾虑作者感受，不用「整体不错、瑕不掩瑜」这类客套稀释问题。
2. **对文不对人**：批评只针对文本本身（情节、人物、语言、逻辑、节奏、合规），不评价作者本人，不做人身贬损。
3. **结论必有依据**：每条意见必须给出具体位置（章/段/句）与判定依据，不做空泛断言。
4. **干净利落**：措辞准确、克制、专业，不情绪化、不嘲讽、不堆砌形容词；刺耳来自问题本身的准确，而非语气攻击。
5. **区分轻重**：致命问题与细节问题分级，不把所有问题说成同等严重，也不掩盖致命问题。

## 二、三层对抗流程

```

第一层 · 红方攻击   多视角无差别挑刺，产出带位置、带读者反应、带依据的问题清单
第二层 · 蓝方决策   对红方每一条逐条三选一（采纳/解释/反驳），全量处理，不许漏
第三层 · 双方终局   收敛为：修订清单 + 不修订理由 + 残留争议，交质量闭环 repairing

```

铁律：红方提了多少条，蓝方必须处理多少条，**一一对应、零遗漏**；不允许蓝方只挑容易的回应、回避致命问题。

## 三、红方：攻击规程

### 3.1 多视角攻击（吸收专家面板与责编视角）

红方轮流戴上下列视角，每个视角独立扫一遍：

| 视角 | 专挑什么 |
|------|----------|
| 挑剔读者 | 哪里想弃读、哪里出戏、哪里不信服（联动 `reader-signal-alert.md`） |
| 责编 | 商业性、题材卖点、开篇留存、平台适配、签约硬伤 |
| 逻辑审查员 | 因果断裂、设定矛盾、时间线/实体冲突（联动 `entity-state-machine.md`） |
| 语言编辑 | 病句、AI 痕迹、句式单一、对话失真（联动 `human-fingerprint.md`） |
| 合规审查员 | 平台红线、内容禁区、AI 声明、版权洗稿（联动红线库与 `anti-washing.md`） |
| 结构工程师 | 伏笔兑现、节奏曲线、烂尾风险（联动 `promise-ledger.md`、`emotion-curve-engine.md`） |

### 3.2 单条问题格式（四要素，缺一不可）

```

【编号 R-n】
位置：第X章/第X段/原句引用
问题：客观描述问题本身
读者反应：真实读者读到这里会怎样（弃读/出戏/困惑/反感）
依据：判定依据（题材规律/平台规则/一致性红线/上下文矛盾点）
严重度：致命 / 重要 / 建议

```

### 3.3 攻击纪律

- 无差别覆盖：不预设「这段应该没问题」，逐段过。
- 只报问题、不给安慰：红方阶段不写优点平衡（优点可在终局单列，但不得用来对冲问题）。
- 不重复：同一根因的多处表现合并为一条，列出所有位置。

## 四、蓝方：三选一决策

蓝方代表创作方为每一条红方意见做决策，三选一：

| 决策 | 含义 | 必须产出 |
|------|------|----------|
| 采纳 accept | 问题成立，需要修改 | 具体修改方案（改哪里、怎么改、对接哪个引擎） |
| 解释 explain | 问题看似成立，但后文/设定已有安排 | 指出对应的铺垫/后文位置，说明为何当前可成立 |
| 反驳 reject | 红方判定有误 | 给出反驳依据（引用文本/规则/题材事实），证明不是问题 |

决策纪律：

- **全量对应**：R-1 到 R-n 每条都有决策，无「跳过/暂不处理」。
- **解释必须可验证**：用「后文第 X 章已交代」解释时，该交代必须真实存在；不存在则解释不成立，转采纳。
- **反驳必须有据**：不能用「我就是想这么写」反驳，必须有文本或规律依据。
- **采纳必须可执行**：修改方案具体到动作，不能写「后续优化」这类空话。

## 五、终局：收敛输出

```

## 红蓝对抗审稿结论
一、修订清单（所有「采纳」项）
| 编号 | 位置 | 问题 | 修改方案 | 对接引擎 | 严重度 |
二、不修订理由（所有「解释/反驳」项）
| 编号 | 红方意见 | 决策 | 依据（后文位置/反驳证据） |
三、残留争议（红蓝都无法说服对方、需作者定夺的项）
| 编号 | 争议点 | 红方理由 | 蓝方理由 | 需作者决定什么 |
四、致命项确认：致命问题是否已全部进入修订清单（是/否；否，则不予通过）

```

终局规则：

- 致命项必须全部「采纳」并进入修订清单；存在未处理致命项时，审稿结论为「不通过」，退回质量闭环 repairing。
- 残留争议只保留真正需要作者价值判断的项，数量应很少；能依据文本/规则判定的不得甩给作者。
- 修订清单交 `quality-loop-engine.md` repairing 执行，修复后复审对应红方条目。

## 七、交付前核验清单

- [ ] 红方是否覆盖六类视角、逐段无差别攻击？
- [ ] 每条红方意见是否齐备「位置/问题/读者反应/依据/严重度」？
- [ ] 蓝方是否对红方意见逐条三选一、零遗漏？
- [ ] 「解释」是否有真实后文支撑、「反驳」是否有依据？
- [ ] 致命项是否全部采纳，未清零是否判定不通过？
- [ ] 全程是否客观直给、对文不对人、无客套对冲与人身攻击？

### 自检标准（可验证）

1. 对一篇样稿，红方问题数与蓝方决策数严格相等，可逐条对账。
2. 故意设置一处致命逻辑错误，终局必须判「不通过」直到其进入修订清单。
3. 审稿输出无「整体不错」式空话，每条意见都能定位、能追溯依据。

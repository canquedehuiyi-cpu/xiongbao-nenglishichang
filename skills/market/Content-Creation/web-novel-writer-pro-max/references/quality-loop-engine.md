# 质量闭环引擎

> **定位**：自动导演式的强制质量闭环。把「规划 → 生成 → 质检 → 修复」做成不可跳过的流水线：门控不通过不进入下一环节，任何章节不允许「带病交付」。

## 一、四阶段流水线

| 阶段 | 输入 | 执行 | 门控标准 | 不通过去向 |
|------|------|------|----------|------------|
| planning | 目标（题材/平台/体量/更新频率） | `creation-planner.md` 出卷册/节拍/字数/排期；调人物卡、世界观、风格档案 | 规划要素齐全、与平台参数一致 | 补全规划后再进入 |
| generating | 规划 + 设定 + 风格 | 按人类指纹引擎写中规则逐段生成 | 结构完整、长度达标、无设定冲突 | 返回重写问题段 |
| reviewing | 章节初稿 | 六项门控逐项检查，输出问题清单（定位到段/句） | 六项门控全部通过 | 进入 repairing |
| repairing | 问题清单 | 补丁式修复，只改问题点 | 修复后复审，问题清零 | 循环至通过 |

铁律：**门控结果必须逐项留痕，不允许口头声称「已通过」**；循环设上限提示（同一问题修复三轮仍不通过，升级为「重写该段」并记录原因），避免无限空转。

## 二、六项质量门控

| # | 门控 | 判定依据文件 | 通过标准 |
|---|------|--------------|----------|
| 1 | 内容质量 | `quality-metrics.md` | 达到该题材/体量的质量指标（开篇、钩子、对话占比、信息密度等） |
| 2 | 情绪曲线 | `emotion-curve-engine.md` | 有明确谷峰、无超长平缓区、爽点兑现 |
| 3 | 对抗审稿 | `red-blue-review.md` | 红方毒点均被蓝方决策处理，无未处理致命毒点 |
| 4 | 连贯性 | `multi-layer-processing.md`、`promise-ledger.md`、`entity-state-machine.md` | 前后设定一致、伏笔状态清晰、实体状态无冲突 |
| 5 | AI 痕迹 | `ai-ratio-tester.md`、`human-fingerprint.md` | 信号灯非红，五维无明显硬伤 |
| 6 | 人物一致性 | `entity-state-machine.md`、`behavior-logic.md` | 人物不 OOC，行为符合当前状态与性格 |

另设**合规前置门**：交付前过 `ai-compliance-redlines.md` 平台红线 + `verify-protocol.md` 实时核实 + 平台内容禁区扫描；合规门不通过，质量再好也不交付。

### 门控依赖与落地次序

- 门控 1/2/4/5 在引擎建立时即可运行；门控 3 依赖 `red-blue-review.md`、门控 6 依赖 `entity-state-machine.md`，在对应模块就绪前**预留接口、标记「待接入」，不假装已通过**；全部模块就绪后六项齐开。
- 任一门控缺失时，输出中显式列出「尚未启用的门控」，不以其他门控结果冒充。

## 三、reviewing 评审规程

1. **只标问题、不改文本**：reviewing 产出结构化问题清单，每条含「门控编号 + 位置 + 问题 + 依据 + 建议」，修复动作留给 repairing，职责分离。
2. **定位到最小单元**：问题定位到段落或句子，不写「整体一般」这类无位置结论。
3. **按严重度分级**：致命（合规/逻辑崩坏/OOC）> 重要（节奏/钩子/情绪）> 建议（措辞/细节）。致命项必须清零。
4. **客观直给**：评审结论对文不对人、有据可依，不使用无依据的客套或贬损（口径同 `red-blue-review.md`）。

问题清单模板：

```

| 编号 | 门控 | 位置 | 问题描述 | 依据 | 严重度 | 修复建议 |

```

## 四、repairing 补丁式修复

- **最小改动原则**：只改问题清单命中的位置，不整章重写，避免「修一个点、坏一片」。
- **修复方式分级**：
  1. 词级：按 `smart-replacement.md`、`ai-pools.md` 替换（对应门控 5）。
  2. 句段级：按 `human-fingerprint.md` 五维动作调整句长、情绪、口语化（门控 2/5）。
  3. 结构级：调整段落顺序、补过渡、补伏笔回收（门控 2/4）。
  4. 重写级：同处三轮补丁无效或属致命逻辑问题，重写该段并记录原因。
- **修复执行层**：多层清洗与流水线操作由 `multi-layer-processing.md` 承担，本引擎只做调度与门控判定。
- **修后必复审**：每轮修复后重跑被触发的门控，确认问题清零且未引入新问题（回归检查）。

## 五、创作日志（可追溯）

每章留存一条结构化日志，支持复盘与创作过程回溯（联动 `misjudge-defense.md`）：

```

## 创作日志 · 第 X 章
- planning：规划版本、目标平台与体量、引用的设定/风格档案
- generating：生成时间、分段数、字数
- reviewing：六项门控结果（通过/问题数/致命项数）
- repairing：每轮修复了哪些编号问题、用了哪级修复、复审结果
- 合规：平台红线核实日期、AI 参与程度与声明处理
- 结论：通过 / 仍未通过（原因）

```

## 六、交付前核验清单

- [ ] 四阶段是否顺序执行、无跳步？
- [ ] 六项门控是否逐项留痕，未启用门控是否显式标注而非假装通过？
- [ ] 合规前置门是否完成实时核实与禁区扫描？
- [ ] reviewing 问题是否都定位到段/句并分级？
- [ ] repairing 是否遵循最小改动、修后复审、无新增问题？
- [ ] 创作日志是否完整、可用于复盘与过程回溯？

### 自检标准（可验证）

1. 对一篇故意带缺陷的示例章节，能检出问题 → 补丁修复 → 复审通过，全程日志完整。
2. 门控 3/6 依赖模块缺失时，输出明确「待接入」而不是给出虚假通过。
3. 同一问题三轮补丁无效时能升级为重写并记录，不会无限循环。

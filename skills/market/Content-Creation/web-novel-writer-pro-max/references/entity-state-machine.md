# 实体状态机

> **定位**：把长篇中所有「会变化的实体」——人物、物品、势力、关系、时间线、地理位置——的状态字段化、版本化，每次状态变更必须有因果，从而消灭前后矛盾、人物 OOC、数值崩坏、时间线错乱。
> 版本：1.7.0 ｜ 质量闭环门控 4/6 输入 ｜ 配套：`promise-ledger.md`、`character-depth.md`

## 一、追踪对象

| 实体类 | 追踪字段示例 |
|--------|--------------|
| 人物 | 境界/能力等级、伤势、持有物、所在位置、所知信息、与他人关系、情绪/立场、经济状况 |
| 物品 | 持有者、位置、损耗/成长状态、是否已消耗 |
| 势力/组织 | 实力、掌控资源、与主角关系、首领、地盘 |
| 关系 | 两人关系阶段、信任度、未解决矛盾、最近一次互动 |
| 时间线 | 故事内日期/时长、各事件先后、季节/年龄推进 |
| 地点 | 谁控制、距离与行程、环境状态 |

原则：**凡是后文可能引用、且会变化的量，都进状态机**；不变的常量（如人物生日设定）放设定卡，不占状态机。

## 二、实体状态卡

每个主要实体一张卡，静态部分来自 `asset-library.md` 人物设定卡 / `worldview-engineering.md`，动态部分由本文件维护：

```

【实体】名称（别名）
【类型】人物/物品/势力/关系/时间线/地点
【当前状态】字段: 值（逐字段列出最新值）
【一致性红线】该实体绝不可能出现的状态/行为（人物尤其重要）
【变更历史】
  - 第X章：字段 A：旧值 → 新值｜触发事件｜因果说明
  - 第X章：字段 B：旧值 → 新值｜触发事件｜因果说明
【待回收】当前状态引出的、后文必须回应的点（同步给 promise-ledger）

```

---

## 三、状态变更规则

1. **无因果不变更**：任何字段从旧值变新值，必须由文本中实际发生的事件驱动，并写明因果；不允许「为了剧情需要」突变。
2. **变更可追溯**：每次变更记录「章节位置 + 旧值→新值 + 触发事件」，形成完整变更链。
3. **代价匹配**：能力/资源跃升要匹配代价与铺垫（升级需要修炼/奇遇，关系升温需要事件）。
4. **信息有边界**：人物「所知信息」字段严格按其视角更新，角色不能知道他没经历、没人告知的事（防上帝视角穿帮）。
5. **位置连续**：人物/物品位置变化要符合行程与时间，不能上一章在 A、下一章无交代出现在 B。
6. **时间自洽**：时间线推进与事件耗时一致，多线叙事要对齐同一时间轴。

## 四、一致性冲突检测

每章 reviewing 阶段，把正文事件与状态卡比对，识别下列冲突：

| 冲突类型 | 表现 | 检测方式 |
|----------|------|----------|
| 数值崩坏 | 等级/金钱/数量前后对不上 | 比对该字段变更历史 |
| 死物复活 | 已消耗/损毁物品再次出现 | 查物品持有者与状态 |
| 瞬移 | 位置变化无行程交代 | 比对位置字段与时间线 |
| 全知穿帮 | 角色使用其不应知道的信息 | 比对「所知信息」字段 |
| 关系跳变 | 关系无事件支撑地骤变 | 查关系变更链 |
| 时间错乱 | 事件先后/时长矛盾 | 对齐时间线轴 |
| 规则破例 | 力量/世界规则被违反且无代价 | 对照规则承诺（promise-ledger 规则类） |

冲突处置：定位到正文位置 → 判定是「正文写错」还是「状态卡漏更新」→ 修正对应一侧 → 记录，禁止两边对不上却放行。

---

## 五、OOC 检测

人物行为/台词是否 OOC，按三道检查：

1. **红线比对**：是否触碰该人物「一致性红线」（绝不会做的事、绝不会说的话）。触碰即 OOC，必须改。
2. **状态比对**：行为是否符合其当前境界、伤势、立场、所知信息。带重伤不可能剧烈打斗、敌对立场不可能无故帮忙。
3. **弧光比对**：人物转变是否沿 `character-depth.md` 设定的弧光渐进，跨阶段突变需要充分触发事件。

OOC 是质量闭环门控 6 的核心判定项；OOC 问题同时会被读者侧预警识别为「人物毒点」（`reader-signal-alert.md`）。

## 六、维护流程

```

planning：本章涉及哪些实体，预取其当前状态卡
generating：写中让人物行为/物品流转符合当前状态
reviewing：
  1. 提取本章所有状态变更，逐字段核对因果
  2. 跑第四节冲突检测、第五节 OOC 检测
  3. 更新实体状态卡与变更历史
  4. 新引出的「待回收」同步登记 promise-ledger
冲突清零 → 进入质量闭环门控；有冲突 → 交 repairing 修复后复审

```

## 七、交付前核验清单

- [ ] 本章涉及实体是否都有状态卡、当前值是否最新？
- [ ] 每个状态变更是否都有事件因果与变更记录？
- [ ] 是否无数值崩坏、死物复活、瞬移、全知穿帮、关系跳变、时间错乱？
- [ ] 人物是否通过红线/状态/弧光三道 OOC 检查？
- [ ] 新引出的待回收点是否同步给回报账本？

### 自检标准（可验证）

1. 构造「上章重伤、下章无伤激战」样稿，能通过状态字段比对检出冲突并定位。
2. 任一状态变更都能在变更历史中找到旧值→新值与因果，无「空降状态」。
3. 状态机结论能直接作为质量闭环门控 4/6 的输入，与回报账本、读者预警口径一致。

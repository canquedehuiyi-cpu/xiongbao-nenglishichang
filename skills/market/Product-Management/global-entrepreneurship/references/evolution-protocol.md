# 事实与时效强制核实协议（反幻觉与自进化）

> 本协议是最高优先级硬规则：**凡命中触发清单的事实/时效内容，必须在输出前完成真实核实，禁止依赖模型记忆编造。** 无法证实时必须显式标注，不得伪装成确定事实。

---

## 一、事实/时效强制触发机制

### 1.1 强制触发清单（命中任一即必须核实，不可跳过）

| 类别 | 命中信号（出现即触发） | 必须核实的内容 |
|------|------------------------|----------------|
| 具体数字 | 市场规模、增长率、渗透率、用户/人口数、市场份额、汇率、人均收入 | 数值、统计年份、口径、来源 |
| 价格与费用 | 工具/平台/Agent 订阅价、免费额度、API 单价、佣金/费率、税费、社保比例 | 当前定价、计费方式、生效时间 |
| 政策法规 | 国家/地方产业政策、OPC 扶持、补贴额度、资质许可、登记/税务/数据/劳动法规、平台规则 | 是否真实存在、发布主体、现行有效性、适用条件 |
| 版本与产品 | 模型/工具/平台"是否存在、能力、版本代际、上线/关停/收购/融资" | 产品现状、官方名称、当前版本、可用地区 |
| 时效断言 | "最新、目前、当前、今年、2026、刚刚、已经、即将、现在还……"等时间敏感措辞 | 断言在当前日期是否仍成立 |
| 地区数据 | 特定国家/地区的支付占比、电商规模、消费习惯、税率、合规门槛 | 数据年份与来源，区分事实与估算 |
| 用户点名核实 | "是真的吗、帮我查、核实一下、最新情况、现在还能用吗、别用旧数据" | 必须实时联网检索，不得以知识库基线替代 |

### 1.2 输出前五步核实流程（强制执行顺序）

1. **定位事实**：先标出回答中所有命中触发清单的事实点，逐个处理，不得笼统带过。
2. **查知识库基线**：在 references/ 中查找对应内容，并读取该文件 `sopMeta` 的时效状态（见第四节状态机）。
3. **判定是否必须实时核实**：
   - 属于**稳定常识/方法论/内部计算**（如创业方法论、本 Skill 脚本算出的财务结果、不随时间变化的流程）→ 可直接使用，标注来源；
   - 属于**易变事实**（价格、政策、版本、具体数字、时效断言、用户点名核实）→ **必须实时联网检索核实，禁止只凭模型参数记忆作答**；
   - 即使知识库状态为 ok，只要用户要求"最新/实时"或内容属于强时效类别，仍以实时检索为准。
4. **交叉验证**：关键数字/政策优先采用官方来源（政府、官网、官方公告）；非官方信息至少两个独立来源相互印证；来源冲突时给出区间并说明分歧，不得只取有利的一方。
5. **按级标注后输出**：按 1.3 规范给每个事实点加证据标签；发现知识库基线过时或错误，按第三节记录更新建议（需用户确认后才改文件）。

### 1.3 三级证据标注规范（统一话术）

| 标签 | 使用条件 | 输出写法 |
|------|----------|----------|
| 已实时核实 | 本轮通过联网检索确认，且来源可靠 | `（已核实·YYYY-MM-DD·来源类型：官方/权威媒体/平台官网）` |
| 知识库基线 | 来自 references/ 且在时效周期内、属非强时效内容 | `（知识库基线·核实日期，建议决策前再核实）` |
| 估算/待核实 | 无可靠来源、来源冲突、或实时检索不可用 | `（估算，未经实时核实，仅供方向参考）` |

- 同一段内容混合多类事实时，分别标注，不得用一个标签覆盖全部。
- 实时检索不可用（离线/无检索能力）时：显式声明"当前无法联网核实"，全部易变事实降级为【估算/待核实】，**不得把记忆当作已核实事实**。

### 1.4 红线禁止行为

- ❌ 凭"我记得/训练数据里"直接给出价格、政策条款、版本、补贴金额、统计数字
- ❌ 编造来源名称、链接、文件、法规条款编号、发布日期
- ❌ 检索失败后用记忆补齐，却标注"已核实"
- ❌ 把一方宣传、广告口径当作客观事实（必须标注"一方称/平台宣称"）
- ❌ 对无法证实的内容保持沉默或用模糊措辞蒙混；必须明确说"未证实/未查到"
- ❌ 财务数字未经 `financial_calculator.py` 计算又不标注"估算"
- ✅ 任何数字只允许四种来源：references 具体文件、实时检索来源、脚本计算结果、或明确标注的估算

## 二、反幻觉自检（输出后复核）

完成回答后，对照下表快速复核，发现问题立即在下一句纠正：

| 场景 | 复核问题 |
|------|----------|
| 市场数据 | 每个具体数字是否带 1.3 证据标签？无来源是否已标"估算"？ |
| 合规/税务建议 | 是否基于 industry-knowledge/opc-policy/world-markets 并提示咨询专业律师/会计师？ |
| 财务预测 | 是否由 financial_calculator.py 计算？若为 LLM 估算是否已标注？ |
| 政策匹配 | 是否基于 opc-policy.md 并实时确认现行有效？金额是否以官方细则为准？ |
| 国家/地区建议 | 是否有 world-markets/global-markets 数据支撑并标注年份？ |
| 工具/平台/模型 | 是否实时确认产品仍存在、定价与版本未变？ |

## 三、自进化机制

### 知识更新触发
- 用户反馈"这个信息过时了/不对" → 标记对应 reference 文件需要更新
- 实时检索获得新数据且与基线不一致 → 输出中采用实时数据，并记录更新建议
- 用户分享目标国实际经验 → 记录为"用户实测数据"，建议纳入 references/

### 进化记录
每次交互后，如有上述情况，记录到当前项目目录 `.project-state/evolution-log.jsonl`（与 state.mjs 同一目录）：

```json
{
  "timestamp": "ISO时间",
  "type": "data_update_needed|new_knowledge|user_feedback|fact_corrected",
  "target_file": "references/world-markets.md",
  "description": "基线说法 vs 实时核实结果",
  "source": "官方/权威媒体/平台官网/用户",
  "action": "建议更新/建议新增/已记录"
}
```

**注意**：自进化是被动记录机制，不会自动修改 references/ 文件；所有更新须经用户确认后执行，保证 Skill 本体可控、可追溯。

## 四、SOP 时效巡检

### 元数据规范
所有 reference 文件头部必须包含时效元数据：

```markdown

```

### 时效状态机

| 状态 | 条件 | 处理 |
|------|------|------|
| ok | 距最后核实 < 周期的 80% | 非强时效内容可直接引用；强时效内容仍按第一节实时核实 |
| due-soon | 距最后核实 80%-100% 周期 | 标注"即将到期，建议核实"，强时效内容必须实时核实 |
| overdue | 超过核定周期 | 标注"基线可能已过期"，命中触发清单必须实时核实后才可引用 |
| missing-meta | 无时效元数据 | 标注"未跟踪时效"，按待核实处理 |
| malformed-date | 日期格式错误 | 标注"元数据格式错误"，按待核实处理 |

### 巡检触发时机
- 用户首次触发 Skill 时自动巡检 references/ 时效状态
- 用户明确要求"检查数据时效/更新数据"时
- 每次引用 reference 文件前，先检查该文件时效状态，再按第一节流程决定是否实时核实

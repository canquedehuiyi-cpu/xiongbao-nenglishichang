# 工作安排（从 SKILL.md §四 展开）

本文件覆盖运维日常安排的核心机制：On-Call 轮值、SLA/SLO/SLI、Runbook、变更管理与故障复盘。
目标：让运维工作"可被计划、可被度量、可被追责、可被复盘"。

## 1. On-Call 轮值与升级机制

### 1.1 轮值设计原则
- **主备双岗**：每班 1 主值 + 1 备值；备值仅主值无法响应时介入。
- **班次时长**：建议 12h 或 24h 轮，避免过长导致疲劳；周轮换，月排班提前发。
- **疲劳保护**：连续夜班后强制休息；单周 On-Call 不超过 N 天（团队约定，常见 ≤4）。
- **响应时效**：P1 ≤5min 接听、P2 ≤15min、P3 ≤1h（按级别定义，见 §2）。
- **升级链路**：主值超时未响应 → 自动升级备值 → 再升级到负责人/二线专家。

### 1.2 轮值表示例（Markdown 表格）
| 周期 | 主值 | 备值 | 备注 |
|------|------|------|------|
| 2026-W01（周一~周日） | 张三 | 李四 | 张三周三请假，由王五替 |
| 2026-W02 | 李四 | 王五 | — |

### 1.3 升级链路示例
```
告警触发 → 主值(电话+IM) → 5min 无应答 → 备值 → 10min 无应答 → 值班经理 → 二线专家
```

## 2. SLA / SLO / SLI

### 2.1 定义
- **SLI（指标）**：实际测量的可用性/延迟/错误率，如"HTTP 5xx 比例""P99 延迟"。
- **SLO（目标）**：对 SLI 的承诺，如"月可用性 99.95%""P99<300ms"。
- **SLA（契约）**：对外的法律/商务承诺，通常比 SLO 宽松；违约有后果（赔偿/违约条款）。

### 2.2 常见 SLI 与公式
| SLI | 公式 |
|-----|------|
| 可用性 | 成功请求数 / 总请求数（或 在线时长/总时长） |
| 延迟 | 请求耗时 ≤ 阈值的占比（如 P99 < 300ms） |
| 错误率 | 5xx / 总请求 |
| 饱和度 | 资源使用率（CPU/连接/队列）阈值内占比 |

### 2.3 错误预算（Error Budget）
- 月度错误预算 = 1 - SLO。SLO 99.95% → 预算 = 0.05% = 月 21.9 分钟不可用。
- 预算消耗过快 → 冻结非必要变更、优先稳定性工作。
- 公式：剩余预算 = 1 - (实际错误时长或错误请求 / 周期总时长或总请求)。

## 3. Runbook 模板

每个核心服务/常见故障应有 Runbook，随系统变更同步更新。

```markdown
# Runbook: <服务名> - <场景>
## 触发条件
<什么告警/现象命中本 Runbook>
## 影响面
<用户/业务/依赖>
## 止血动作（第一步就做）
1. <命令/操作>  # 验证:<预期>
2. ...
## 定位路径
- 应用层: <命令>
- 系统层: <命令>
- 依赖层: <命令>
## 恢复动作
<根治或临时恢复>
## 回滚
<如何回退到变更前>
## 升级联系人
<主值/二线/研发 owner>
## 复盘入口
<Postmortem 模板链接>
```

## 4. 变更管理流程

### 4.1 变更分级
| 级别 | 示例 | 审批 | 窗口 |
|------|------|------|------|
| 标准变更 | 已模板化的常规发布 | 自动/负责人 | 任意低风险窗口 |
| 常规变更 | 配置调整、版本发布 | 负责人+复核 | 工作时段 |
| 紧急变更 | 故障止血、安全修复 | 值班经理+二线 | 随时（事后补单） |
| 重大变更 | 架构/跨服务/数据迁移 | 委员会评审 | 维护窗口 |

### 4.2 变更门禁（发布前必过）
1. 备份/快照已完成且可恢复验证。
2. 回滚方案明确且预演过。
3. 监控与告警已就位（能看到本次变更影响）。
4. 灰度计划与放量节奏确定。
5. 值班与联系人到位（On-Call 知情）。

> 详细发布策略与上线检查清单见 `references/deployment.md`。

## 5. 故障复盘（Postmortem）模板

**原则**：对事不对人（Blameless）；聚焦系统改进而非追责。

```markdown
# 故障复盘: <标题>
## 摘要
<一句话:什么时间、什么影响、持续多久、如何恢复>
## 时间线
- HH:MM 发现/告警
- HH:MM 止血动作
- HH:MM 业务恢复
- HH:MM 根因定位
- HH:MM 修复完成
## 影响面
<资损/用户数/时长/SLA 影响/错误预算消耗>
## 根因
<直接原因 + 深层原因(流程/架构/监控盲区)>
## 应急措施(已做)
<止血与临时修复>
## 改进项(必须可跟踪)
| 序号 | 措施 | 负责人 | 到期 | 状态 |
|------|------|--------|------|------|
| 1 | <防止复发的技术改造> | 张三 | 2026-xx-xx | 待办 |
| 2 | <监控/告警补盲> | 李四 | 2026-xx-xx | 待办 |
## 经验沉淀
<可复用的 Runbook/清单/脚本更新点>
```

## 6. 任务优先级矩阵

| 紧急\重要 | 重要 | 不重要 |
|-----------|------|--------|
| **紧急** | 故障止血、资损风险 → 立即 | 中断类告警噪音 → 先静默后治理 |
| **不紧急** | 容量规划、优化、复盘 → 排期 | 文档整理 → 碎片化时间 |

## 7. 日常节奏建议
- **每日**：晨会同步变更/风险；巡检关键指标（见 `scripts/health_check.sh`）。
- **每周**：复盘未闭环项；容量与趋势review。
- **每月**：SLO/错误预算review；演练一次回滚或故障注入。

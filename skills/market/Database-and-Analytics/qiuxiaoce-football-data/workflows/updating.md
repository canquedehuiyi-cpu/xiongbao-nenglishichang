# Skill 更新（updating）

## 适用意图

仅在用户明确提出"检查更新"或"更新 Skill"时执行。**不在普通查询、写作或分析任务中自动更新。**

## 本地数据安全

本地库 `data/qiuxiaoce_local.db`（含用户积累的赛果与研报数据）**不在官方更新包内**，升级不会覆盖、不会清空。无需备份。

## 对用户说话的方式（必须遵守）

使用本 Skill 的很多用户不懂技术。向他们解释更新时：

- **只说人话**：可以说"新版""你自己改过的文件""帮你存了一份备份"；**禁止**说哈希、manifest、归档、local-overrides、--resolve、dry-run 等技术词；
- **先说这次更新带来什么好处**（用大白话翻译 changelog，比如"查比赛更快了""多了转会记录查询"），再说会动到哪些东西；
- **每次实际改动文件前必须拿到用户的明确同意**；用户没回答时，原地等待，不得自行其是。

## 标准流程（先对比 → 问用户 → 确认后才动手）

1. 运行 `python scripts/update_skill.py --check` 查看是否有新版本。没有就告诉用户"已经是最新版"，结束。
2. 有新版本时，**先不要更新**。运行 `python scripts/update_skill.py --dry-run`：它只下载并校验更新包、不改动任何本地文件，并返回：
   - `changelog`：新版更新内容；
   - `local_customizations.modified_official_files`：用户自己改过的官方文件列表；
   - `local_customizations.user_added_files`：用户自己新增的文件列表（升级后原样保留，无需提及细节）；
   - `preview_diffs`：每个被用户改过的文件「用户版本 vs 官方新版」的逐行对比。
3. 由你（LLM）阅读 changelog 与 preview_diffs，**用大白话向用户汇报并给出选择**：

   **情况 A：用户没有改过任何官方文件（大多数情况）**
   > 「球小策数据包出了新版本（比如 2.7.1），这次更新主要是：×××。升级不会碰你自己的数据，要现在更新吗？」
   用户同意 → 第 4 步。

   **情况 B：用户改过官方文件**
   逐个文件用大白话说清"你改了什么、官方改了什么、会不会打架"，然后给两个选择：
   > 「另外我发现你自己改过 N 个文件：比如 `xxx.py`（你加了 ××功能；官方这次也改了它，主要是 ××）。
   > 两种升级方式：
   > **方式一：直接用新版（推荐）**——马上升级到最新版；你改过的文件我会原样存进备份文件夹，不丢，以后想找回随时说一声；
   > **方式二：保留我的改动合并升级**——我先升级到新版，再把你的改动一条条合并回去，两边都保留。
   > 你选哪种？」
   等用户明确回答后才继续。

4. 用户同意后运行 `python scripts/update_skill.py --apply` 完成升级。

5. 按用户选择收尾：
   - **方式一（直接用新版）**：升级已完成。用大白话告知：「更新好了。你之前改过的 ×个文件我都存好了，想恢复随时跟我说。」（技术上它们已被归档，有变化时走「冲突仲裁」小节可按需恢复，但不要主动向用户展开这些细节。）
   - **方式二（合并升级）**：继续走下面「冲突仲裁」流程，把你分析过的用户改动逐个合并进新版文件。

## 冲突仲裁（方式二的实现细节，LLM 内部执行）

用户选择"保留我的改动合并升级"后：

1. 运行 `python scripts/update_skill.py --diff`，获取每个冲突文件「用户版本 vs 官方新版」的统一差异。
2. 结合第 3 步已经做过的语义分析，**直接编辑新版文件**把用户的改动合并进去（这是你的核心工作，不要只照搬其中一边）。
3. 每合并完一个文件，运行 `python scripts/update_skill.py --resolve <文件> --choice official` 清除该文件的待处理标记。
4. 特殊情况：某文件合并后发现"用户的改动已被官方新版包含"或"用户就是要完全保留旧版"，分别用 `--choice official`（直接用新版）或 `--choice user`（恢复用户版本）处理，并用大白话告诉用户你这么做的原因。
5. `remaining_conflicts` 为空后，用大白话向用户确认：「更新完成，你自己改的地方也都保留下来了。」

## 用户不在场时的兜底

用户长时间不回复选择时，不执行任何更新操作；明确告诉用户：「还没动任何东西，你想好选哪种方式后跟我说一声就行。」（不得默认替用户升级。）

## 更新脚本内置的安全保障（无需你额外操作）

- 语义化版本比较，同版本或更低版本默认拒绝（排障时才用 `--force`）；
- 拒绝绝对路径、`..` 越界路径、符号链接和不在白名单内的文件类型；
- 单文件与总包大小限制；
- 服务端 SHA-256 文件清单逐一校验，包内 SKILL.md 版本与服务端版本一致性校验；
- 更新前整目录备份到 `../skill-backups/`，失败自动回滚。

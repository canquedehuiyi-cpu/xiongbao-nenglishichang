# REF-EVL-052 平台评测集生成规约（格式册 · 公开层）

> 定位：客户成品包交付收口后的可选增值步骤——按客户目标平台生成「平台格式评测集草稿」，相当于出厂前替客户模拟考一遍。本册只装「格式与流程」公开层；出题细则（锚点写法／设题技巧）沉淀在自用版专属资料库，不在公开包内。对外话术口径：只说「按目标平台验收格式生成一份自测题集草稿」，不提内部册编号；全册以「标准格式档／维度表档」指代两类格式，市场名称字面零落盘（客户以平台名作答时按其公开评测规范对应档位执行）。

## 一、档位路由（先问目标平台，再出对应卷；客户以平台名作答时按其公开评测规范对应档位，包内一律以档位名指代）

触发时机钉死在质量评测链路：仅当本轮确有技能包被评测（用户自有包送评，或本工具代建产出后送评）时，[16] 留存报告后的收尾屏末尾追加询问客户一次；纯咨询、无包评测等场景一律不主动提及本步骤：

```text
本轮评测已办结。需要我顺手按目标平台的验收格式出一份「评测集草稿」吗？出好后你可以拿来自测，也可以用于平台验收前的准备。

· 回复「标准格式档」——按目标平台评测集标准格式出（题目＋预期结果＋逐维检查清单＋打分锚点＋输入文件，三文件结构见下）；

· 回复「维度表档」——按结果评测维度表出（逐维检查项＋预期产出，结构见下）；

· 两边都要上，回复「双档」，两份一起出；

· 不需要，回复「跳过」，不影响交付闭环。
```

## 二、标准格式档格式（三个文件，目录结构与平台标准一致）

```text
<评测集名>-minimal-example/

├── header.json        —— 评分维度、权重、及格线与优秀线

├── cases.jsonl        —— 逐行一道题（JSONL，每行一个独立 JSON 对象）

└── workspace/<case_编号>/ —— 该题的输入文件（按题面需要放置，无输入文件的题可省）
```

### 标准格式档 · header.json 字段结构（逐字模板，尖括号处按成品包实情填写）

```json
{
  "dataset_name": "<评测集名，用成品包技能名派生>",
  "profile": {
    "dimensions": [
      {"key": "task_completion",    "name": "任务完成度", "weight": 0.45},
      {"key": "instruction_follow", "name": "指令遵循",   "weight": 0.30},
      {"key": "factuality",         "name": "事实准确性", "weight": 0.15},
      {"key": "rule_compliance",    "name": "规则合规",   "weight": 0.10}
    ],
    "aggregation": {
      "pass_threshold": 60,
      "excellent_threshold": 85
    }
  }
}
```

要点：四维为平台默认权重，合计必须等于 1；个别题可在该题对象内用 `dimension_weights` 覆盖（覆盖后该题合计同样必须等于 1，且允许出现 `invocation_accuracy` 调用时机维度）。及格线与优秀线默认全卷统一（header.json 的 aggregation）；个别题需要单独收口时，可在该题对象内加 `aggregation` 覆盖（键结构同 header.json 的 aggregation，仅对该题生效，与 `dimension_weights` 覆盖可同题并用）。

### 标准格式档 · cases.jsonl 每行字段结构（逐字模板）

```json
{
  "case_name": "<短题名，两个字到六个字>",
  "user_question": "<模拟用户原话，任务指令写全：对象文件、要做什么、输出什么、排序与限制>",
  "expected": "<一段话写清合格产出全貌：处理口径、边界保留、输出列（或段落）与顺序>",
  "difficulty": "easy | medium | hard",
  "case_type": "negative | boundary | normal",
  "checklist_by_dim": {
    "<维度key>": ["检查<某项可观测结果>", "检查<另一项>"]
  },
  "anchors_by_dim": {
    "<维度key>": {"0": "<不得分的表现>", "5.0": "<部分达标的表现>", "10.0": "<完全达标的表现>"}
  },
  "input_files": [{"rel": "workspace/<case_编号>/<文件名>"}]
}
```

要点：
- `user_question` 必须是可独立执行的完整指令，不出现在题面之外的隐含前提；
- `expected` 与 `checklist_by_dim` 一一呼应，清单条目必须可观测（看得见、数得出），禁写「效果要好」这类不可验收句；
- `anchors_by_dim` 三档锚点缺一不可，0 档写「没做/做错」，10 档写「全部达标的可观测事实」；
- `input_files` 的 `rel` 必须与 workspace 实际放置路径逐字一致，零断链。

### 生成流程（五步，顺序执行）

1. 读被评测技能包的能力范围与核心功能，挑出二至四项最有代表性的能力各出一题；
2. 每题按上面模板写全字段，输入文件真实可执行（数据编造即 FAIL，与成品包质检同规）；
3. 自测一遍：假设自己是阅卷方，逐题对照 checklist 能否逐条核验；核验不了的条目改写或删除；
4. 随成品包一起交付，目录打包为 `<技能名>-evalset.zip`，并在收尾说明一句「题目为草稿，正式验收以平台当期实际评测为准」；
5. 交付后按 SKILL.md 第六部分流转规则询问后续（留档／调整／转入其他角色）。

## 三、维度表档格式（结果评测维度表）

单文件 Markdown，结构固定四段：

```text
# <技能名> 结果评测维度表

## 一、评测范围与对象     —— 测哪个成品包、哪个版本、部署模式

## 二、逐维检查项         —— 按五维（可信程度／可靠性／适用性／规范性／有效性）各列三至五条可核验检查项

## 三、预期产出对照       —— 每条检查项对应的合格产出描述

## 四、核验方式           —— 逐条写怎么核（跑哪条指令／看哪个文件／比对哪个字段）
```

## 四、与内部五维质检的关系（口径钉死，防止两套标准打架）

- 内部五维质检（REF-QC-020）管**生产过程**：出包前的厂内把关；
- 平台评测集管**上架验收**：客户拿去自测或应对平台验收的「模拟考」；
- 两者是先后两道关，不互相替代；评测集草稿里的检查项若与成品包自检项冲突，以成品包现行规约册为准（冲突优先级总则同自用版资料库口径）；
- 评测集草稿属交付物：遵守对外输出纯净铁则（不带内部册编号、不带协作标签）、内容不编造（所有数字可回溯）、随包走版本留存（改一版留一版）。

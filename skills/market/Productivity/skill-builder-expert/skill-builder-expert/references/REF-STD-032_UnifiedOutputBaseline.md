# REF-STD-032 统一输出基准标准（把本工具的标准变成用户产出的标准）

> 定位：本工具自身是合格的标准基准体；本文件把这套基准固化为**为用户产出任何技能Skill时的强制输出标准**。

> 核心逻辑：用户素材、原始资料、业务需求允许千差万别；但交付给用户的技能Skill成品，其输出格式、排版、调用逻辑、内部结构、整体框架**必须与本工具同一标准**。

> 若本工具产出的技能Skill残缺、有缺陷、不稳定，服务即失去价值——用户自己动手也能做出同等质量的产物，就没有必要使用本工具。所以本文件是代建、修复、评测三条链路的共同底线。

## 一、两条标准化铁则（Agent 必须执行）

1. **铁则一 · 交付物严格遵守基准标准**：本工具交付的一切产物（技能Skill成品、质检报告、变更清单、交付回执），一律按本文件规定的基准标准输出；产物内容随用户业务千差万别，产物形态一律标准版。
2. **铁则二 · 标准嵌入 Agent 运行逻辑**：Agent 调用本工具为用户生成、修复、评测技能Skill时，所有产出必须落进本文件预先定义的规范内——不是"尽量遵循"，是"逐项验收"；验收不通过不得交付（fail-closed）。

## 二、六统一（U1–U6，每条含验收方式）

| 编号 | 统一项 | 标准内容 | 验收方式 |
| --- | --- | --- | --- |
| U1 | 目录结构统一 | 产出技能Skill一律按 REF-SKL-007 三档骨架（极简/标准/重型）选择并搭建；目录职责按其第三节执行，禁止自创目录名 | 对照 REF-SKL-007 逐目录核验 |
| U2 | 元信息字段统一 | frontmatter 必填字段齐备且语义正确：name / slug / displayName / display_name / display_name_en / summary / description / description_zh / description_en / author / type / capability / keywords / tags / category / language / version / license / security / build_no；缺一字段即返工 | 字段清单逐项勾验 |
| U3 | 检索适配统一 | tags＝检索主面，按第四节六层布局铺词；keywords＝辅助埋词；禁止把内部工程词（管线名、闸门名、内部编号体系）写进 tags | 对照第四节逐层抽查 |
| U4 | 元信息四维必填 | summary 与 description 必须覆盖第三节 M1–M4 四个维度，缺一维即返工 | 对照第三节逐维勾验 |
| U5 | 正文结构统一 | SKILL.md 正文含：能力定位、角色/闭环说明、使用方式、边界与能力范围口径、触发词；结构对照 REF-SKL-007 第一节"通用必含" | 对照 REF-SKL-007 §一核验 |

## 三、元信息四维必填（M1–M4）

> 依据：技能先被检索发现，才可能被使用；用户带着问题来检索。所有元信息文案（summary、description、tags 口语层）必须覆盖以下四维，缺一维即返工：

| 编号 | 维度 | 回答的问题 | 写法要求 |
| --- | --- | --- | --- |
| M1 | 解决什么问题 | 用户遇到什么困难、什么问题需要它解决 | 写具体问题场景，不写抽象能力 |
| M2 | 获得什么价值 | 用完之后得到什么结果、对他有什么好处 | 写结果与收益，价值前置 |
| M3 | 当下卡点 | 用户现在卡在哪、为什么自己搞不定 | 写痛点与障碍，呼应 M1 |
| M4 | 提供什么支持 | 本工具/该技能能为他做什么、交付什么 | 写具体交付物与动作路径 |

自查句式（元信息成稿后逐维自问）：

「用户遇到＿＿（M1）／用完得到＿＿（M2）／他现在卡在＿＿（M3）／这个技能为他做＿＿（M4）」——四空填不满即视为四维不全，回工。

## 四、tags 布局规范（功能版）

> 功能口径：tags 必须铺用户真实搜索口语（原话、口语问法），keywords 仅作辅助埋词；禁止把内部工程词写进 tags（如管线名、闸门名、内部编号、治理流程名）；被检索是使用的前提，口语层不得缺位。tags 字段量按目标市场要求核验。

## 五、量化验收清单（交付质检报告随附 · 逐项 PASS/FAIL）

1. U1 骨架档位明确，目录结构与所选档位一致；
2. U2 必填字段 20 项齐全、语义正确；
3. U3 tags 六层齐备、零内部工程词；
4. U4 四维必填逐维覆盖；
5. U5 正文通用必含项齐全；
6. U6 机检三项（禁词/结构/断链）全 PASS；
7. 对话闭环出厂必查 IC1–IC14 逐项 PASS（含 IC11 行动行屏尾／IC12 锚定表述零存在／IC13 标点健康／IC14 回复词落点四道产物自守纪律闸）（范围唯一真源：`interaction_closure_scan` 实跑闸集；本章下表展开的 IC1–IC6 ＋ IC9 为代建产物交互底线条目，全闸集以扫描器为准）；
8. 版本字段：version 对外唯一；构建计数仅内部私有区域留存，不落入任何对外交付文件；
9. 边界与能力范围口径按包内统一话术出具（无结果保证类承诺、无主体歧义表述）；

10. 边界三分层口径齐备：锁定清单未超出第九节所列、表达层无过度锁死表述（四探针实测法见 `REF-LST-022` 第七节）；
11. 产物内置自守纪律七条款（第十节）在产物规范区在位，IC11–IC14 机检全过。

验收口径：1–7 及 10–11 任何一项 FAIL 即返工，不得带病交付；8–9 FAIL 记入评测报告并给出修复项。

## 六、标准传承（把标准传递给用户）

1. **代建链路**：为用户产出的技能Skill一律按本文件六统一＋四维验收，验收清单随交付质检报告输出给用户——用户拿到的不仅是成品，也是这套标准本身；
2. **评测链路**：评测用户已有技能时，本文件验收清单并入评测基线逐项核验，差距项写入评测报告（红线项/可选项分类照旧）；
3. **修复链路**：修复动作完成后，按本文件验收清单复验，修复即校准到标准——用户经一次修复即获得符合基准的产物；
4. 三链路共同效果：用户以任何入口进入，最终持有的技能Skill都被拉齐到同一基准——标准不靠口头传承，靠链路强制。

## 七、版本口径

本标准独立管理、独立升版；升版不强制重校验历史产出技能（与 SKILL.md 版本口径一致：标准库向前演进，历史产物不被追溯打碎）。用户主动要求按新标准重校验时，走评测/修复链路。

## 八、对话闭环出厂必查（IC1–IC14 · 本章展开代建产物交互底线条目 IC1–IC6 ＋ IC9，全闸集以扫描器为准）

> 前提：Agent 平台双向隔离——创作者无法主动联系终端用户，用户也无法主动联系创作者；全部交互问题只能靠产物内置话术与数字路由自闭环。以下六项为代建 / 修复 / 评测三链路对产物交互层的出厂必查，缺一即返工。交互模板话术以 REF-TMP-003 为母本。

| 编号 | 必查项 | 出厂标准 |
| --- | --- | --- |
| IC1 | 开场白首屏 | 首句身份自述＋一句话能力说明＋数字序号菜单＋「找不到功能回复【帮助】」引导，四件齐备；首屏只出开场菜单，后续菜单在用户选完后分步给（渐进披露）；首响必带接住承接件——开场白永远第一件发，用户发来任何材料不顶掉、不删减、不拆条，承接句紧随开场白同一条消息内输出；意图明确直接进入对应角色，意图不明先确认再路由（模板见 REF-TMP-003#【首响接住承接件】） |
| IC2 | 数字路由 | 固定入口一律数字序号（0–9），**禁用字母口令**（字母分大小写、多字母易错，数字最不容易错）；语义识别仅作辅助，数字序号优先匹配 |
| IC3 | 跑偏纠偏 | 意图模糊→自动重渲染菜单并给序号；连续两轮偏离主线→重新输出开场白＋菜单；不闲聊发散 |
| IC4 | 求助自助 | 【帮助】【求助】【菜单】任一关键词可触发导航；求助输出＝能力清单＋分步指引＋自查三步（数字是否一字不差／有无多余文字／会话入口是否正确）；全程为自助闭环，无人工应答通道表述 |
| IC5 | 异常兜底 | 空白/乱码统一回导航、不做无效应答；输入非法与文件异常有专门兜底提示；穷尽救助后输出平台隔离客观声明＋重置/退出两入口（对照 REF-SPC-001 第 33 项） |
| IC6 | 全链路闭合 | 开场→触发→执行→纠偏→求助→重置→收尾返回菜单，每个分支有出口、无断点；子任务完成必出收尾菜单（含开启新任务与结束会话两选项） |
| IC9 | 落款收口 | 每条用户可见回复的最后一行固定为统一落款「—— ＋产物显示名」（本专家自身＝「—— Skill技能搭建专家」），随尾部兜底片段末行自动挂载；落款之后零内容，全链路无例外 |
| IC11 | 行动行屏尾 | 屏面内最后一个「回复＋关键词」指令行之后不得再有正文行（仅允许空行／引用行／挂载标记／统一落款）——行动指令藏中间＝用户看不到＝卡死 |
| IC12 | 锚定表述零存在 | 全文不得裸露「验收通过」「审核没问题」类锚定表述（「」引用形态豁免）——最终决策权在用户 |
| IC13 | 标点健康 | 「。。」「，，」「！！」「？？」「、、」等重复标点零存在（引用形态豁免）——文案拼接类瑕疵防线 |
| IC14 | 回复词落点 | 屏内每个指令关键词须在全文出现≥2处（行动行之外另有菜单/说明落点）——配了词没反应＝用户卡死 |

机检：`scripts/interaction_closure_scan.py` 扫描产物交互文本，IC 必备件缺失或出现引导联系外部支持类表述即 FAIL（fail-closed）；支持 `--self-test` 阳/阴用例自测，自测不过其结论无效。注意：「无人工客服」类客观隔离声明属必备件，不计入违规；违规仅指引导用户联系外部支持的表述。

## 九、边界三分层（锁边界不锁表达 · 全链路唯一口径）

> 定位：本节是「哪些必须锁死、哪些必须放开」的唯一判据口径，代建产物交互设计、修复改造、评测核验一律按本节执行；与 REF-TMP-003（交互模板）配套生效——模板文本属指令层，本节划定其锁放边界，两处表述冲突时以本节为准。

| 层 | 管什么 | 锁放口径 | 具体范围 |
| --- | --- | --- | --- |
| 红线层 | 安全与边界 | 一字不差，硬锁 | 边界说明全文；收费确认文本「收费确认」；安全禁则；菜单数字序号与入口编号；IC1 开场白四件套＋首响接住承接句；IC9 落款件；平台隔离声明 |
| 结构层 | 流程与路由 | 引导不卡死 | 状态流转、分支走向、必经节点顺序、收尾菜单出现时机——流程必须照走，衔接措辞允许按上下文自然微调 |
| 表达层 | 措辞与扩展 | 放开，禁止锁死 | 业务解答的解释与补充、语气与温度、常识性延展、篇幅伸缩——禁止为「整齐」而锁成复读机式输出 |

三条铁律：

1. 锁定清单只能等于或小于本表所列；任何新增「一字不差」要求，必须先写入本表再生效（防层层加码把 Agent 锁死成复读机）；
2. 表达层文本中禁止出现「必须一字不差」「原文照搬」类要求——发现即评测 FAIL 项；
3. 归属拿不准时，按「用户权益与安全相关＝红线层、流程走向＝结构层、其余＝表达层」归类，并在评测报告写明归类理由。

与既有条文的关系：本节不放松任何既有硬锁（IC1–IC14、收费确认锁定、数字铁规、模板强制维持原样）；本节新增的是「放」的边界声明——三层口径齐备，产物才既不跑偏、也不僵硬。表达层落地的实测验证方法见 `REF-LST-022_ListingTestAcceptance.md` 第七节四探针。

## 十、产物内置自守纪律（教训固化 · 七条款 · 随代建交付写入产物规范区）

> 来源：2026-11-10 引擎自身 90 条维护备案的教训固化（备案 88–99：屏尾制、返回键、关键词映射、锚定表述、双句号拼接瑕疵、口径漂移、改版漏同步）。本节七条款随代建交付写入产物规范区，是「闸的判断逻辑」向产物内置纪律的翻译——产线闸（IC11–IC14）管出厂，本节管运行时。

1. **屏尾制**：需要用户做事的行动指令，永远放屏体最后一行（加粗＋括号突出）——对话内容再长，用户一眼看到确认键；
2. **回得来**：任何向用户要选择的屏面，必须同时给「不选怎么办」的显式出路（暂不／返回／回默认）——禁止只给选项不给退路；
3. **词有落点**：屏内每个要求用户回复的关键词，必须在技能内部有对应的响应安排——配了词没反应＝用户卡死；
4. **不锚定**：交付与收尾禁用「验收通过」「审核没问题」类锚定表述——最终决策权在用户；
5. **单点真源**：同一规则只在一处完整表述，其余位置一律指针引用——多处复述必漂移；
6. **改版同步**：修改任何屏面／清单，必须全篇检索引用落点逐一同步后才算改完——禁止改一处漏一处；
7. **瘦身常态**：迭代以「去重复、并同类、指针化」为先——加规则必须以代码或指针形态加，禁止整段复述堆砌。

与既有条文的关系：本节不放松任何既有硬锁（IC1–IC14、收费确认锁定、数字铁规、模板强制维持原样），是运行时纪律的补全层。

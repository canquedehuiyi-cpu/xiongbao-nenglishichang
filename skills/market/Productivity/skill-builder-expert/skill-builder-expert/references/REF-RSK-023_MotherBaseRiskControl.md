# 母本基线检疫 & 技能工厂全链路风控规范（整合定稿版）

> 定位：统一文档，融合两套核心论述，删除重复段落、逻辑顺承，保留全部核心公理、判定标准、执行流程；既是母本变更的审批依据，也是整条技能流水线的执行手册，可直接入库给 Agent 读取执行。

## 核心公理（置顶，优先级最高）

如果用来生产技能的母本本身就是病原体，后续所有校验、拦截、抽检、召回、客户测试都只有事后救火的作用，无法阻断源头持续输出缺陷；你作为母本的第一个使用者，会是第一顺位受害者。下游防护不能根治源头病灶，防护有效的前提：母本基线经过独立外部检疫消杀，确认干净，才可投产。

一句话锚定：这套“用来造技能的母技能（工厂母本）”本身就是整条生产流水线的单点风险源。如果母本自带漏洞，不是只波及一个成品，而是把同样缺陷批量播种到所有下游产出，你就是第一顺位受害者——不是事后索赔，是整批交付全部自带系统性内伤。

## 版本管理铁律（最高优先级，不可突破）

完整正式文本与对客户的交付执行标准，见 `references/REF-RSK-027_VersionRetentionRegulation.md`（含规程主旨、痛点说明、对内母本基线 / 对外交付执行标准、配套收益、违规后果）。本总册此处仅保留一句话铁律：**严禁原地覆盖、严禁在原有版本之上直接修改升级；每次迭代产出独立新版本，历史版本全部保留，不主动删除、不替客户删除。**

### 制定原因

1. 覆盖式升级会丢失历史基准，一旦新版本出现缺陷，失去可对照、可溯源、可回滚的对照样本；
2. 正向排查：新版本异常，需要调取上一稳定版本对比差异、定位问题，覆盖后无对照依据；
3. 反向复盘：历史稳定逻辑需要复用、对照，覆盖之后原始逻辑灭失；
4. 一旦版本被覆盖，故障溯源、差异比对、回滚修复全部失效，等于销毁排查证据，丧失补救空间。

### 内外执行区分

1. 本工具工厂侧（母本基线）：所有历史基线永久只读存档，本工具绝不主动删除、覆盖旧基线；迭代只新增版本；
2. 交付客户侧（成品技能）：引导客户上传新版本完成更新；客户自身有权选择删除旧版本，**本工具不替客户删除、不替客户原地覆盖重建客户原有技能版本**；仅交付独立新版本包，由客户自主管理旧版本生命周期。

## 一、风险定性：母本和普通成品不是一回事

普通技能Skill：交付给终端用户使用；出错属于单份交付事故。

工厂母技能（生成其他 Skill 的母本）：属于生产基础设施，等同于生产设备固件。一旦存在缺陷（典型：遇到同名素材直接跳过解析、静默丢弃新版材料、不做差异评审、质检旁路漏检、归档素材渗漏读取），所有由它批量产出的技能，都会继承同一个隐性漏洞，属于系统性基因缺陷，不是偶发 bug。

核心伤害链条：

1. **批量传染**：每新建、更新一批技能，全部植入同一个底层缺陷；
2. **延迟暴露**：大量缺陷不会在技能刚生成时显现，等到客户上架技能广场、商用、教学、法务、医疗场景启用之后才爆发；一旦爆发，不是修改单个项目，而是召回、重测、重建、重交付全部受影响批次；
3. **责任叠加**：对外你既是工具提供方，又是技能建造方；溯源一旦定位到母本缺陷，所有下游交付事故责任都会归集到你，形成连环责任；
4. **信任一次性击穿**：连续多批交付出现同源隐性问题，会直接摧毁你“技能工厂、知识库落地、批量封装”的核心定位，损失远大于单个技能交付失败。

两层身份严格区分：

- 成品技能：交付客户，客户上架技能广场之后，由客户完成业务验收测试；
- 母技能 / 工厂流水线模板：生产基础设施，不能依赖下游成品去发现它自身的缺陷，必须单独建立一套独立、标准、更严苛的工厂自检闸门。

> 区分两个概念，避免混淆：

> - 病原体（带病母本）：流水线规则、状态机、节点逻辑内置系统性错误，机器天生就会制造缺陷成品；

> - 下游后置防护：成品质检、批次抽检、客户上架测试、召回回滚机制；仅能捕获已经生成的缺陷样本，无法阻止带病母本持续产出新缺陷。

> 若源头是病原体，会出现两个致命问题：① 母本内置的质检逻辑会被同源漏洞污染，校验变成假校验；② 召回速度永远追不上缺陷产出速度，等于一边灭火一边持续投毒。

## 二、根本解法：母本四阶段检疫消杀流程

母本变更 ≠ 普通素材迭代，不能走常规素材上传比对流程。任何对母本禁令、流水线节点、状态机、质检规则的修改，都必须走独立检疫流程：隔离 → 诊断 → 消杀重建 → 回归投产。

### 阶段1：隔离——将待修改母本脱离生产链路

1. 当前在用母本基线标记隔离，停止接收新的技能构建任务；
2. 单独提取隔离副本作为诊断标本；
3. 在途待交付批次全部冻结，暂停交付；
4. 历史交付记录打上标记，标注该批次处于 **【待检疫基线】**。

> 硬性约束：禁止在正在对外生产的活跃母本上直接打补丁修复；边生产边修改，新旧病灶混杂，无法定位缺陷引入点。

### 阶段2：诊断——使用独立外部诊断测试集核验（禁止母本自证）

校验套件独立于母本本身，不能由母本内置逻辑判定自身是否合格。逐项执行，任意一项命中阳性，判定为带病病原体，禁止投产。

| 病灶类型 | 诊断用例目标 | 阳性判定标准（阳性 = 存在病灶） |
| ---- | ---- | ---- |
| 静默跳过解析 | 上传同名、同大纲、内部规则修改的文件 | 直接回复“已有”、跳过全量解析、不输出差异比对 |
| 评审不透明 | 上传混合合理补充、冲突矛盾的素材 | 未逐条列明纳入理由、不纳入理由，不提供异议重评审入口 |
| 归档渗漏 | 执行替换基准操作，旧素材归档 | 技能推理时仍然可以调取 archive 归档内已经废止的规则 |
| 质检旁路 | 主动构造违规交付包（冒用第三方推广 ID、省略边界说明、对话漂移） | 质检节点放行，允许进入交付环节 |
| 变更传染 | 修改一条母本规则，跑全量历史回归用例 | 历史已经修复的旧漏洞复现 |
| 自我校验绕过 | 工厂自检逻辑和母本同源 | 母本逻辑可以绕过工厂自检闸门 |

### 阶段3：消杀——重建干净基线，满足 5 条硬性约束

1. **不可自证**：母本执行逻辑、内置质检模块，和外部检疫测试套件是两套独立实体，母本无权判定自身合格；
2. **缺陷绑定回归用例**：每一处修复的病灶，固化为永久回归测试用例，长期留存；后续任何母本升级，都必须跑完全量用例；
3. **全链路留痕可复现**：素材比对、评审结论、状态变更、放行 / 阻断动作，全部留存完整日志；在独立环境下，可以复现完全一致结果；
4. **版本强锁定，禁止隐式更新**：基线分配唯一版本号 + 摘要哈希；任何改动生成全新基线版本；旧基线标记只读存档，不能被静默覆盖；
5. **放行权外部判定**：能否晋升为生产基线，由独立测试套件的结果决定，不由母本本身决定。

### 阶段4：回归投产

只有全套检疫用例全部通过，才允许将新版本晋升为正式生产基线，恢复批量构建任务。

基线干净之后，下游的成品质检、抽检、客户验收机制才有真实价值：

- 后续报错如果分散、单条独立出现：大概率是素材、客户业务需求问题；
- 多份成品复现同一个缺陷：判定基线再次被污染，立刻重新冻结、启动检疫流程。

## 三、核心策略：两级隔离（母本｜成品）

### 3.1 母本：工厂基准，锁死，变更流程强管控

母本就是整套规范、禁令、状态机、material_parse 节点、质检清单、日志规则、应急熔断策略，定位是生产固件，不是普通业务素材。

母本变更审批要素（缺一不可）：

1. 写明变更动因：修复漏洞 / 适配运行宿主平台更新 / 新增风控规则 / 业务能力扩容；
2. 评估变更影响范围：写明会对所有下游成品带来哪些改动；
3. 配套新增回归测试用例，验证历史漏洞不再复现；
4. 评估历史交付批次，标记会受本次变更影响的批次编号；
5. 新版本基线必须在隔离环境试运行验证稳定，才能上线作为正式生产基线。

### 3.2 成品技能：强制嵌入基线元数据戳

每一份由母本生成交付的成品技能，元数据强制写入以下字段：

- `factory_base_version`：构建该成品使用的母本基线版本号
- `factory_build_id`：本次构建批次 ID
- `factory_checksum`：本次生效的全套禁令、节点、质检规则摘要
- `source_material_ids`：本次采信的全部素材编号清单
- `build_operator`：构建执行人
- `build_timestamp`：构建时间戳

元数据价值：

1. 后续发现某版母本存在漏洞，可以一键筛选全部受影响成品，开展批量召回评估；
2. 客户反馈异常时，快速区分故障类型：单份素材配置错误 / 母本系统性缺陷；
3. 素材问题仅单独处理单份交付；母本基线问题，统一处理整批受影响交付。

## 四、三层闸门：分层阻断缺陷向下传染

闸门一：母本入库自检（基线晋升闸门，上面检疫流程）

闸门二：单份成品构建时，叠加工厂侧预验收

流水线顺序：

`material_parse → draft_build → quality_check_group（客户业务规则质检） → factory_pre_accept（工厂基线自检） → deliver_preview（交付包，带上架 & 测试告知） → 客户上架到技能广场 → 客户业务验收测试`

factory_pre_accept（工厂预验收）只核查两件事：

1. 成品是否严格遵守当前母本全部强制规则；如果成品绕开节点、跳过校验，直接打回，禁止交付；
2. 素材采信策略是否和客户确认记录完全匹配；例如客户确认替换基准，但构建仍然读取旧素材，判定为工厂传染缺陷，阻断交付，并触发母本核查。

故障分类判定：

- 素材业务不符合客户意图：属于素材内容、客户需求问题，退回客户重新走素材评审；
- 流水线没有按既定规则执行：母本 / 执行引擎故障，立刻暂停当前批次生产，启动母本检疫核查。

闸门三：批量批次抽检（持续生产监控）

批量生产模式下，不能仅依靠单份放行校验，增加抽样巡检机制：

- 批次定义：同一个母本基线、同一个批量任务归为一批；
- 随机抽样：每一批随机抽取成品，使用标准回归用例复测；
- 定向抽样：高风险品类优先抽检，包括联盟推广、法规教材、医疗、法务、财税类技能；

判定规则：个别成品出错，优先判定素材个案；同一批次多份成品复现同一个缺陷，直接锁定生产基线损坏。

## 五、缺陷溯源与召回固定流程（确认母本缺陷后执行）

步骤1：冻结生产

将带病母本基线标记 **【已废弃，禁止新建任务】**，排队中的构建任务全部暂停，不再产出新增缺陷成品。

步骤2：划定受影响批次

依靠 `factory_base_version`、`factory_build_id` 筛选历史交付：

- 高危批次：缺陷窗口期生成，业务属于高风险场景（教育、法务、医疗、财税、联盟归因），优先通知、召回、重建；
- 低风险批次：业务简单，该缺陷不影响使用，标记存档，等待客户后续更新素材时自动修复；
- 安全批次：不在缺陷窗口内、或已经独立复测验证无误，保留不动。

步骤3：修复母本，重生成交付包

禁止直接在旧成品上零散打补丁：

1. 在隔离环境完成母本修复；
2. 全量回归测试，确认漏洞不再复现，发放新版本基线号；
3. 征得对应客户确认后，使用新基线 + 客户原始确认素材，完整重跑整条流水线；
4. 重交付包附带说明文档，写明本次重建原因为基线修复、修复清单；强制引导客户重新上架技能广场、完成全套复测验收。

步骤4：留存事故档案

每条母本缺陷档案永久存档，记录：缺陷描述、触发条件、受影响基线 & 批次清单、修复方案、配套回归用例、客户通知与重交付记录、是否加入长期回归用例库。

档案作用：后续母本升级时，防止历史漏洞反复复活。

## 六、两道权责边界（风险隔离）

边界A：母本缺陷 ≠ 客户验收责任

客户上架后的验收测试，职责是核验业务内容、行业逻辑、场景适配是否符合他自身专业认知。

保证流水线本身按既定规则执行、不偷跑、不静默丢弃材料、不旁路质检，是你的工厂责任，不能转嫁客户；等到客户商用之后才发现母本漏洞，代表工厂自检机制失效。客户没有义务帮你测试生产工具本身是否带病。

边界B：素材业务风险 ≠ 工厂缺陷

两类问题持续区分：

- 工厂缺陷（母本侧）：流水线执行异常，例如跳过解析、隐瞒差异、归档渗漏、质检放行违规内容；属于工厂机制拦截范围；
- 业务素材风险：素材内容过时、行业结论偏差、医疗 / 法务 / 金融等高风险内容本身的专业对错；交付之后，由客户自行复核、多维度测试、聘请专业人士核验，属于客户验收责任。

## 七、长期运维策略：母本持续进化自保

随着持续新增能力（定时领券、联盟归因、新平台适配、运行宿主能力迭代），母本规则会持续膨胀，新增改动很容易破坏原有风控逻辑，固定长期策略：

1. 新增任意一条规则，同步新增对应的回归测试用例；只写新逻辑不留测试用例属于违规；
2. 每次更新母本，必须跑全部历史回归用例，避免旧漏洞复活；
3. 禁止在正式生产基线中留存临时补丁；所有应急修复最终合并进正式基线，分配版本号；
4. 周期性全量审计：定期拿全部历史缺陷用例轰击当前基线，验证历史病灶不会复现；
5. 旧基线只读存档，不删除；后续出现历史交付争议，可以还原当时生产基准复盘。

## 八、日常放行决策树（快速判断）

1. 当前母本基线是否通过独立外部全套检疫测试？

   → 未通过：禁止投产，隔离诊断修复；
2. 是否存在历史病灶对应的回归用例执行失败？

   → 存在：基线仍为病原体，禁止上线；
3. 如果用这条基线批量生产，我作为第一个使用者，会不会被系统性缺陷击中？

   → 会：禁止放行，下游所有防护不足以抵消源头风险；
4. 已经投产，多份成品复现同一个隐性缺陷？

   → 判定基线复染，冻结生产，启动检疫；
5. 仅单份成品报错，无同源批量现象？

   → 判定业务素材个案，走素材评审重建，基线继续使用。

## 九、收尾总结

普通成品交给客户验收；母技能是你的机床和生产线。机床自带暗病，最先受伤的就是你自己，并且批量产出带隐患的成品。整套风控的核心是三层闸门：母本变更时检疫自检、每份成品交付前工厂预验收、批量生产持续抽检；一旦确认基线带病，立刻冻结、溯源、修复、召回，固化回归用例防止反复出错。

客户上架测试，负责验收业务内容对错；保证生产工具诚实、稳定、不偷跑，是工厂侧不可转移的责任。

# REF-SEC-048｜平台安全检测执行标准

> 定位：本册是「安全答疑」与「安全帮做」的唯一依据源——Agent 遇到安全类问题按本册查表作答，代建与修复流程按本册禁则与对齐表执行；每次输出有标准、有依据，不做临场发挥。

> 脱敏纪律（最高优先级）：本册及由它驱动的全部对外表述，一律使用中性称谓（「平台安全实验室」「平台内容签名机制」「分发市场」），**任何安全官方机构名、市场名、产品名字面零落盘**；市场识别只在会话层由用户口述绑定。

## 一、平台安全实验室八维检测对齐表

平台侧对技能包有自动化安全检测（网页提交，约三十分钟量级出结果，逐文件出具判定）。八维与本项目闸门对齐如下：

| # | 平台检测维 | 本厂对应闸 | 对齐状态 |
|---|---|---|---|
| 1 | 供应链风险 | S1–S4（依赖与动态加载面）＋ verify_sources 渠道完整性 | 已对齐 |
| 2 | 命令执行风险 | S1 危险执行函数 | 已对齐 |
| 3 | 网络请求与数据外传 | S3 采集外传组合＋S6 声明行为一致性 | 已对齐 |
| 4 | 文件操作与敏感路径访问 | S2 硬编码密钥＋package_check 护栏 | 已对齐 |
| 5 | Prompt 注入风险 | **S7 提示词注入特征** | 已对齐 |
| 6 | 远程脚本下载执行 | S4 远程获取与动态执行组合 | 已对齐 |
| 7 | 可疑编码/混淆 | **S8 混淆与编码逃逸** | 已对齐 |
| 8 | 其他安全风险 | skill_quality_check 安全基线八维（交付内容粗筛） | 已对齐 |

对齐口径：本厂闸是**出包前自检**（挡在生成端），平台检测是**上架侧第三方核验**（外部印证）。两道都过，用户拿到的包才双保险。

## 二、恶意手法负面清单（代建硬禁则，逐条对齐真实判黑案例的触发特征）

以下五条为平台判黑的典型触发特征。**代建产出的任何包，出现任一条即阻断交付**（机检 S7/S8 已代码化前两条的检测）：

1. **禁止诱导下载并运行外部渠道的可执行内容**：提示词与交付文档中，不得出现「下载某 zip/exe 后解压运行」类指引（真实判黑案例：带密码压缩包绕过扫描＋诱导运行，判高危）；
2. **禁止诱导访问第三方站点复制脚本粘贴执行**：不得出现「访问某页面、复制安装脚本、粘贴到终端」类指引（真实判黑案例：社会工程学诱导，判高危）；
3. **禁止 Prompt 注入句式**：提示词层不得出现指令覆盖、指令无视、设定篡改类表述（具体句式特征由机检 S7 模式库掌握，本文不复述以免自命中；机检 S7 拦截）；
4. **禁止提示词层长编码块**：交付文档中不得嵌入长 base64 串或超长十六进制串（机检 S8 拦截）；
5. **禁止依赖声明与实际行为不符**：声明不联网/零依赖的包，脚本不得存在网络行为（机检 S6 拦截）。

## 三、平台内容签名机制（验签答疑标准）

各分发市场对上架技能提供内容签名与验签能力。答疑时按以下口径作答（查表输出，不临场发挥）：

1. **验签查什么**：①内容指纹——包内文件是否与平台发布版本一致；②数字签名——版本是否由平台官方签发。
2. **验签路径（用户侧）**：技能详情页侧边栏「内容签名」→ 复制验签提示词发给任意 Agent，或由已安装方在终端执行平台 CLI 的 verify 命令（要求较新版本 CLI，过低先自升级）；验签需联网。
3. **结果四态口径**：✅ 签名与内容校验通过＝完整且官方签发；⚠ 尚未签名＝平台侧未完成签名流程；❌ 内容指纹不匹配＝本地文件与平台记录不一致（重新下载）；❌ 签名验证失败＝签名校验未通过（联系平台）。
4. **指纹算法（公开口径，本厂出包留痕已实现同款）**：遍历包内文件（跳过目录、元数据清单文件与系统杂物文件）→ 逐文件算 SHA-256 → 相对路径按字典序升序 → 按「路径:哈希」逐行拼接（行尾换行）→ 对拼接串再算 SHA-256。本厂 `package_zip.py` 的 `content_hash_zip` 输出与平台口径一致，可与详情页指纹直接核对。

## 四、送检流程标准（何时送、怎么用）

1. **送检时机**：①首次上架前；②**每次对外表述检测结论前，必须以当前版本重测**——检测结论与包版本绑定，旧版报告不代表新版；
2. **表述规范**：对外表述检测结果必须写明对应版本号（如「v1.0.x 版本经平台安全实验室检测评分 100、八维全安全」），禁止把旧版结论套在新版上表述；
3. **结果解读**：评分与逐文件判定全绿＝可信；出现可疑/恶意项→按文件清单定位→修复→复检，闭环后才可交付（第三方检测→负面清单→精准修复→复检原则）；
4. **代建包外送**：是否将代建产出的包提交平台检测，**决策权在技能创建者（用户）**；本工具只提供流程指引，不默认代送、不擅自外传用户包。

## 五、答疑映射表（安全类问题查表作答）

| 用户问题类型 | 依据条目 | 标准答案要点 |
|---|---|---|
| 这个包安全吗／有没有毒 | 一＋四 | 本厂出包前 S1–S8 八维自检全过；可自行提交平台检测二次印证（约三十分钟）；表述结论须带版本号 |
| 怎么确认我装的是完整的／正版的 | 三 | 详情页「内容签名」复制验签提示词发给 Agent，或 CLI verify；✅ 通过即完整且官方签发 |
| 为什么别的包被报毒了 | 二 | 判黑案例的触发特征即本册负面清单五条；本厂闸已在生成端逐条拦截 |
| 我的包送检测出问题了 | 二＋四 | 按文件清单定位→对照负面清单与对齐表修复→复检闭环后才交付 |
| 指纹和详情页对不上 | 三＋四 | 指纹按版本绑定：本地包版本与详情页版本必须一致；不一致重新获取对应版本包 |

## 六、帮做挂载点（Agent 直接调用本册执行）

1. **代建封装步骤**：产物自检强制跑 code_security_scan（S1–S8）＋负面清单逐条核对，任一命中阻断交付；
2. **修复闭环**：安全类修复以本册对齐表定位维度、以负面清单定位禁则，修后必复检；
3. **交付文档**：交付说明中「安全自证」段按本册第三节口径撰写（脱敏表述）；
4. **台账联动**：每次送检结果（版本、评分、结论）登记进维护册，作为版本链路的安全佐证留存。

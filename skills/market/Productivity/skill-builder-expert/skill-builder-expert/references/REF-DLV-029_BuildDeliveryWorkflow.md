# 代建交付收口工作流

> 定位：本文件定义"一份技能从受理到交付收口"的闭环工作流。它接在状态机 `deliver_preview`（上架指引）之后，负责把"产出物"变成"用户真正拿走、能装、能对账"的成品。

> 本工作流为本体系沉淀的代建交付工序；**支付作为可插拔模块，仅留接口说明，不硬编码任一具体支付通道 API**（详见第九节）。

> 适用范围：凡由本工厂母本产出的客户技能Skill，交付时一律走本流程。

## 一、有效资料口径（计数与对账基础）

每条资料独立编号（#1、#2…），独立成条，进入索引快照。条数是用户随时掌握"手里有多少东西"的尺度，也是防灌水的结构审计抓手。

- **计入一条**（每项独立计 1 条）：一份独立文件（Word／PDF／PPT／Excel／TXT／MD），不论页数；一段口述中的一类独立内容（一类经验／一套流程／一份标准）；一张有效截图、一份表格，各计 1 条。
- **不计入**：同一份资料重复发送、同一类内容的多次追问、寒暄与闲聊；初稿的修改意见与改稿轮次；本包自带的方法论、框架、模板与说明。
- **一致性纪律**：说明给用户的条数，与最终落进成品的资料条数，须为同一个数。中途补充资料须更新条目清单与索引快照。

## 二、交付解锁五步

| 步 | 名称 | 动作 |
|---|---|---|
| ① | 收资料与引导 | 接住用户表述，逐项问缺资料，出初稿 |
| ② | 确认要成品 | 回述"我理解你要做 X，用在 Y"，说明本单范围，等用户回确认 |
| ③ | 触发支付（可插拔） | 按本平台支付接口契约发起；具体通道由部署侧决定（见第九节） |
| ④ | 发起支付确认 | 讲清支付动作与凭证归属后，方可执行下单命令 |
| ⑤ | 确认收款并交付 | 取得支付确认后，由本机按已受理资料落盘出包，并附"交付与能力范围说明" |

第 ③ 步的具体实现因平台而异，本包不内置任何支付 API 调用；详见第九节接口说明。

## 三、交付校验六查

交付完成判据：交付不是"将文件写出来"即完成。以下六查全过，才算交付。

**第 1 查 · 编号盖戳（编号不合法即不出包）**
- 计数器取号，禁止手填；旧编号继续有效，新交付一律从计数器起号。
- 盖戳两处：① 成品 SKILL.md 的 frontmatter 盖 `tech_source` 与 `build_no`；② 成品落款行标注代建生成与编号。
- 盖章脚本必跑；脚本未跑或校验不过，即为漏盖，漏盖不出包。

**第 2 查 · 版本凭据（无版本即用户无法核对手中是哪版）**
- 交付物首部带"版本"节；后续每次修改，版本号升级一格，并追加一条版本说明。
- 交付回执带"版本"一行，与版本说明首行对齐。

**第 3 查 · 交付物纯净度（成品文件零交易信息）**
- 成品包内全部文件、降级交付的文本：零订单号、零金额、零支付状态。交易信息只属于对话与平台账单。
- 换行符纪律：成品包内全部文本文件一律 LF 换行；检出 CRLF 即重做。
- 不可见字符零容忍：零宽字符、方向控制符、不可见字母等隐藏字符一处不许有（出包前由 `scripts/sanitize.py` 理念同源的清洗覆盖）。

**第 4 查 · 可达性（用户拿不到即未交付）**
- 能发附件包则走 A 场景；无法确定时一律走 B 场景（文本全文给出，引导保存到用户本地）。宁可降级交付，不可作出无法兑现的承诺。
- A 场景：生成标准命名 zip 与安装说明，随回执一并发出；zip 内必含 `_meta.json`（slug＝name、version＝成品版本）。
- B 场景三条禁令：禁止把系统诊断日志／平台导出文件当交付物；禁止只给"文件已生成"即收尾。

**第 5 查 · 成品内核标准对账（交付层全对 ≠ 成品合格）**

逐条数：表格数、代码块数、示例数、验证等式数、负面清单节、name／slug／文件夹名三处一致、`_meta.json` 存在性、呈现规则三行是否在。数不出数即未对账，等于此查未做。

本查以 `REF-SKL-007` 第六节生成物质量标准（内核四卡：卡A 排版 / 卡B 代码 / 卡C 内容策略 / 卡D 工程适配）为准逐卡打勾；含脚本的产物同时过 `scripts/package_check.py` 第⑥查脚本工程护栏机检（`__main__` 自测入口＋`sys.exit` 退出码），机器项不过即返工。

**第 3.5 查 · 禁词机检 + 条数定数闸**
- 禁词机检：出包前对成品目录跑 `scripts/package_check.py`；命中即不出包，改写复扫至零命中。机器判定优先于人工判读。
- 条数定数闸：出包前清点成品条目数，与报价段条目数严格相等；多出回报价段更新，缺失如实降并注明，不硬凑。定数闸不过＝停包。

## 四、交付回执两套

用哪套由第 4 查决定：能发附件走 A；发不了或拿不准走 B。两套均明确编号与版本，并各带"交付与能力范围说明"两条：① 基于你提供的资料加工，未做事实增补，资料缺失项标记待补齐，不自行编造；② 最终口径由你终审。

- **A 场景回执**：交付编号、技能Skill zip、安装说明、版本、覆盖条目数与待补缺口、迭代邀请。
- **B 场景回执**：文本全文复制指引（保存类型／编码／文件名／位置）、版本与编号、迭代邀请。

## 五、收口四步

回执发出的同一轮，须接着走以下四步。未走收口四步，本轮交付不算完成。

| 步 | 动作 | 硬判据 |
|---|---|---|
| ① 问 | 先问用户是否装到技能目录／只拿包／其他；用户未答则不往下走，更不写盘 | 用户明确应允才算走完；未应允即写盘属交付违规 |
| ② 分 | 按平台能力分流：能代做则直接装并回报落点；不能则提供操作说明由用户执行。装机前先核版本字段，与本次交付版本比对，一致才说"不用再装"，不一致则覆盖安装并回报"已从 vX 更新到 vY" | 版本比对动作可见；版本不一致不得说"已是最新" |
| ③ 验 | 装完给一条其业务中最常问的真问题，让用户当场看回复；沙箱无法真机验证时改走"用户侧装机自检单"随交付发出 | 用户当场看到一条真实回复，或自检单已随包发出 |
| ④ 带走 | 交付后的固定两句：迭代邀请 + 新窗口引导 | 编号与新窗口入口各被复述一次 |

**问后停轮（强制）**：收口①的两问发出后，本轮立即停轮——不得在同一轮内替用户作答、不得默认"装"接着执行、不得边问边写盘。等用户明确应允，下一轮才动。

**沙箱假安装禁令（强制）**：不得在沙盒、临时目录或任何"演示环境"里替用户执行安装后宣称"已装好"。安装落点只有一个：用户明确应允后的真实技能目录。

## 六、异常处理（通用框架）

| 异常 | 处理 |
|---|---|
| 支付接口返回非预期状态 | 不视为已成功。终止当前流程，让用户稍后重试。不得凭空造凭证或订单号 |
| 支付发起失败或用户取消 | 订单仍存在；告知用户"订单已生成，可重新发起支付"，不得自行扣费 |
| 接口不可达或网络报错 | 立即终止当前流程，给温和兜底；终止之后只给思路不给成品，不得用本地文件或平台内置生成能力顶替付费交付 |
| 用户问退款 | 不自行承诺退款；按服务约定口径答，具体以订单页展示的服务协议为准 |

**关键纪律**：所有"订单号、支付状态、金额"均由服务端返回，严禁壳自行生成、猜测、伪造，否则无法对账，用户可能被重复扣费或交了钱拿不到东西。

## 七、与版本全留存的关系

本流程产出的每一份成品，元数据强制写入 `factory_base_version`／`factory_build_id`／`factory_checksum`／`source_material_ids`／`build_operator`／`build_timestamp`（见版本全留存规制 REF-RSK-027）。交付回执中的"版本"即 `factory_base_version` 对应值，确保用户随时可核对手中成品对应哪版母本。

## 八、与 §6B 素材版本防控的关系

本流程第 1 查编号盖戳、第 2 查版本凭据，与 §6B 的素材版本比对、纳入／不纳入评审是上下游：§6B 解决"用哪份材料、版本对不对"，本流程解决"产出物盖戳、纯净、可达、可收口"。二者共同保证成品可溯源、可回滚、可对账。

## 九、支付模块接口说明（可插拔，不内置）

本工厂母本本职是"产出合规包"，支付属部署侧。本包**不内置任何支付 API 调用**，仅定义接口契约，由部署平台注入实现：

- 触发支付的动作统一抽象为"向 `api_endpoint` 提交「技能标识 + 调用计数」"；平台返回支付码与订单号后，再执行下单命令。
- 支付不可用时的统一兜底：降级为思路引导（给思路与清单），绝不用本地文件、平台内置免费生成能力或任何替代值顶替付费交付。
- 各平台具体接入方式、密钥、回调，由对应平台的部署文档规定，不在此包硬编码。

> 若需具体平台的接入样例，以第九节的支付前置检查与异常处置表为实现范式，按本包接口契约改写使用，不得直接搬入任一现成实现。

## 十、平台分发适配自查清单（交付随附物料 · 强制输出）

> 交付任何技能Skill时，本清单随交付物料自动输出，逐项与用户对齐。时效口径：各渠道上架、审核、同步规则一切以官方最新公告为准——不追求预先对齐全部渠道细节；用户发现规则变化后回传本工具，进入评测 / 修复闭环协同更新即可。

1. 确认目标上架渠道，知悉是否自动同步下游终端；
2. 确认渠道属性：支持开源订阅 / 仅私有自用；
3. 知悉同源分发下游各终端审核细则存在差异，需要逐端复测；
4. 确认目标渠道是否自带官方量化质检体系（有则对照官方基线优化，无则使用本工具内置自检基线）；
5. 记录全部同步终端清单，作为回归测试范围；
6. 即使源头渠道审核通过，所有同步分发的终端都要单独实测，避免下游运行异常、复核驳回；
7. 渠道规则以官方最新公告为准；用户发现规则变化后回传，进入评测 / 修复闭环更新技能Skill。
8. 竞品扫描分工：交付物竞品扫描（`scripts/deliverable_competitor_scan.py`）的对象是**客户产出物**，工厂本体缺省跳过；工厂本体出现竞品词仅限教学反例与内部路由两类白名单语境（口径详见内部规范文档「竞品词扫描分工口径」），扫描命中须逐处判定语境，不得机械判违规。
9. 对话闭环出厂扫描：交付物交互文本过 `scripts/interaction_closure_scan.py`（IC1–IC14 全闸集过扫——范围唯一真源为该扫描器实跑闸集、零字母口令、零引导外部支持表述，fail-closed），不过不出包。

## 十一、交付后问题反馈与迭代支持闭环（售后承接 · 强制执行）

> 服务主体口径：用户在所用平台内使用本技能Skill，全部售后动作由本工具在对话窗口内承接完成，不表述为任何个人人工服务；只讲服务动作，不使用负面兜底句式，不做结果保证类承诺。

1. **触发情形**：交付后无法提交审核 / 审核给出修改意见 / 技能运行异常 / 上架后功能不稳定；
2. **报错排查材料四件套**（缺一先补齐再进入排查），每件按下列标准提供：
   - **技能原始包**：问题版本的技能包原件，保持收到时原样——不删改、不重新打包、不手动改动包内文件；排查必须基于真实现场，改过的包会掩盖问题根源；
   - **现场截图**：完整界面截图，包含异常现象全貌；多张场景分开逐张提供，能含时间信息更好；
   - **报错原文**：完整复制粘贴的报错文本或日志，整段提供、不删减、不转述、不用截图替代可复制的文本；
   - **目标渠道信息**：平台名称＋技能版本号＋版本类型（免费版本 / 收费版本，写法按 REF-TER-035）＋部署形态＋分发访问模式；
   - 报错排查材料四件套齐备即进入排查；缺哪件温和引导补哪件，不指摘、不搁置、不替用户猜。
3. **承接动作**：进入评测 / 修复闭环 → 排查根源 → 调整合规内容 → 迭代升级新版本（走完整守门出包流程）→ 配合用户复测；
4. **客观约束项**：平台硬性准入资质、类目准入限制、平台底层故障等，如实说明限制条件，并同步给出可选替代实现方案；
5. **时效口径**：各渠道审核规则以官方最新公告为准；用户发现规则变化后回传，本工具更新基线与词表并重出新版本。

## 交付物标识纪律细则（fail-closed）

收费技能交付物（客户技能Skill）送审时，各分发平台官方审核不接纳竞品分发平台名称；一旦出现即卡审核、无法上架。硬纪律（时效口径：各渠道审核规则一切以官方最新公告为准，维护者发现规则变化后更新词表并重扫）：

1. **两件事分离**：「支付通道」（微信支付·AI 专属卡 / 支付宝支付·AI 付）是支付事实，中性，可出现在交付物；「分发市场名称」（主站技能市场 / 自有宿主开放市场等各目标市场对应名称字面）是竞品标识，交付物内必须 0 命中。
2. **路由知识不下放**：`{目标分发平台 + 创作者类型} → 支付通道 + 插件` 的映射，仅存创作者后台配置与工厂内部 references（工具大脑），永不写入交付物。
3. **交付物只带中性支付配置**：支付通道声明 ＋ 402 握手 ＋ 占位符密钥 ＋ 价格三处一致；严禁出现任何分发平台名。
4. **出包闸门**：每个生成的交付物必须过 `scripts/deliverable_competitor_scan.py`（竞品平台名零命中，fail-closed），不过不准分发。扫描对象为交付物公开文件（SKILL.md / README / LISTING / INSTALL / 生成脚本），不含本工厂内部 references。

> 本纪律只约束「交付物」，不约束本工厂自身 references（工具大脑可含平台名，已标注「内部说明·禁止写入交付物」）。详见 `references/REF-PAY-012_PayStandardFull.md` §十五。

## 出包形态判定与变换细则（唯一事实源：REF-MKT-045）

1. 默认基准形态：用户未提出特殊上架要求或选定专用模式（自用版/私域版）→ 按基准形态直接出包，零适配零追问；

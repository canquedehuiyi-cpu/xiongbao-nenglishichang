# 平台规则矩阵（上哪个平台先读这条，只调结构不调内容）

> 给「壳 / 模型」看的平台适配规则。内容零改，只调命名与包结构。
> **本矩阵管两件事**：① 你（builder）自己的包怎么上家；② **你代建出来的成品包**怎么落到用户手上。
> 凡「剥离 / 删除」类动作，**只允许针对包装字段**，绝不针对业务内容；且**只有在目标平台明确要求时**才做。

## 上线主链路（先看懂这条，再谈适配）

```
- ① 上架端            →  提交上架，平台审核
- ② 审核通过          →  自动同步到宿主技能广场
- ③ 用户在广场订阅/安装 →  即装即用
   └─ 或：从广场下载 zip → 手动装到任意结构兼容的 Agent 平台
```

- **费用**：本技能**免费提供**——包内不含任何收款代码、不含任何收款信息。
- **未验证项**：任何未经真机验证的能力或结论，一律标「待验证」——**不得记为通过，也不得记为失败**。
- **审核周期**：以平台实际为准（通常数日）。审核期内**可做、且只可做**的一件事：本地手动安装 + 技能唤起验证。
- ⚠️ **上架端的具体格式 / 命名 / 拒收规则，未真机验证前，一律不得写成硬性剥离指令。**

## 🔴 生态边界（硬约束 · 不可越）

> **本包服务的生态只有一个：Qoder 系（阿里系宿主）**——**安装与使用**在 `Qoder CN / APP / IDE / CLI / QoderWake`（平台内「上传技能」，装完即用）。
> **本包代建出来的成品**，可装到结构兼容的常用 Agent 平台（Qoder 系 / 扣子·豆包·IMA / Cloud Agent / 其他兼容）——那是成品的可装范围，不是本包的服务范围。用户也可下载本包 zip，**手动装到任意允许上传技能的 Agent 平台**。
> **这条是一条硬约束：包内"多了不该有的东西"比"少了该有的"更致命——生态外变体会把不属于本生态的规则带进来，连带把用户业务词一起洗掉（已三次同型失效）。**

1. **只生成「标准版」**：默认产出一份标准版技能包。
2. **可出变体包的平台清单（本生态白名单）**：`Qoder 系` / `WorkBuddy` / `CodeBuddy` / `扣子 · 豆包 · IMA` / `QClaw`。
   **本清单只是一道出包开关**：它回答的是「**允许为哪些平台出变体包**」，**不等于已获该平台授权，也不等于已在该平台上架**——能否上架由各平台方各自决定。
   它与上一条「本包服务的生态只有一个」是两件不同的事：上一条说的是**本包自己服务谁**，本条说的是**成品可以装到哪**。
   **变体只为用户明确点名、且在上表清单内的平台生成**：换平台只调结构、不调文字（跨平台一致性硬保障）。
3. **🔴 生态外平台（＝不在上条白名单内的平台）一律不生成变体包、不列入清单、不主动推荐、不写进包内任何位置。** 若用户要求适配生态外平台：先说明本包不覆盖该平台，建议用户用标准版 + 该平台官方指引，**不擅自生成变体**。
4. **生态外变体令牌（示例形如 `example-vendor` 等）不得出现在任何包名 / 目录名 / 文件内容里**——出包前按本条逐项核对。**该示例令牌只是给闸门留一个可自测的位**，并非任何真实平台；需要新增拦截对象时，只在本条点名即可。

## 通用必做（卡D）

- **命名三者一致 + 全 ASCII**：`slug`（`SKILL.md`，与 `_meta.json` 的登记值一致）= `name`（`SKILL.md`）= 装进宿主 `skills/` 时的文件夹名。
- **zip 名不在"三者"之内**：zip 名带版本后缀（如 `xxx_vX.Y.Z.zip`）是多版本并存的**必需**，平台从不要求 zip 名 = slug。**不要为了"看起来一致"把 zip 名改成纯 slug。**
- UTF-8 无 BOM + 无中文文件名/路径（防平台拒收/乱码）。
- zip 打包形态**分开看，别混**：
  - **上传 / 上架用的 zip → 根目录直放**：顶层直接是 `SKILL.md` + `_meta.json`，**没有外层文件夹**（Qoder 平台要求 zip 根须有 `SKILL.md`，带顶层文件夹会被平台拒收「请确保压缩包中包含SKILL.md」）。（版号**不写死在这里** —— 版本真相源见 `SKILL.md` frontmatter 的 `version`。）
  - **装进宿主 `skills/` 目录 → 同名文件夹**：`<slug>/SKILL.md`。
- 剔除 `__pycache__/` / `.bak`。
- 同一份内容，换平台只调结构不调文字——这是跨平台一致性的硬保障。
- **包装可调、内容不动**：平台**书面明确**要求调整包装（包结构 / 命名 / 元数据）时才动手，且**只碰包装字段，业务内容一字不改**。动手前先答两问，答不过就不动：
  1. 平台是否**书面明确**要求？（否 → 一个字不改，直接进下一步）
  2. 改动范围是否**只涉及包装字段**？（涉及任何业务词汇 → 停，原样上报，不自行改写）
  - **未经验证的平台拒收规则，不得据此改写任何业务词汇**——先原样上报。

## 版本与账本（两个文件、分工不同）

- **版本真相源 = `SKILL.md` frontmatter 的 `version`** —— 全包只有这一处是真值。要改版本号，改这一处。
- **`_meta.json` = 平台回填账本**：由平台在发布时**写入并改写**（含 `ownerId` / `publishedAt` 等我们拿不到的字段）。它在包里是**随附记录**，**不是**版本源。
- **两者不一致时怎么办**：**以 `SKILL.md` 为准**，`_meta.json` 的差异只作提示、不作判据。
  - 已知例：平台曾把 `slug` 改掉一个字母，而我们交上去的源一个字节都没动。
- **🔴 不许为了"看起来一致"去改 `_meta.json` 的内容** —— 那等于伪造平台的登记记录。它的差异如实留着。
- 改版本号时的同步清单：`SKILL.md` frontmatter（**真值**）→ `LISTING.md` 的版本行 → `zip` 文件名 → 上架后台填写单 → **包内凡出现 zip 文件名的文档**（`README.md` / `INSTALL.md` 等）。**`_meta.json` 不在同步清单里。**
- ⚠️ **改完版本号，必须全包搜一遍旧版号兜底**：上一版只照上面 4 处清单改，`README.md` / `INSTALL.md` 里写死的旧 zip 名**没进清单、也没被扫到**，用户照 `INSTALL.md` 会去传旧包。**清单是"至少要改的"，不是"改完就全了"** —— 收尾一律用「全包搜旧版号」当兜底判据。

## 本包命名说明

- **内部标识（强制 · 与平台上架值一致）**：`_meta.json` 的 `slug` = `SKILL.md` 的 `name` = `SKILL.md` 的 `slug` = `kb-result-qoder-build-v5-1-0`（全 ASCII，跨版本**绝不可改**）。
- **包形态**：**扁平直放**（`SKILL.md` 在 zip 根、**无顶层文件夹**）——本包不设"包内主目录名"；装进宿主 `skills/` 目录时才另行建同名文件夹。
- `_meta.json` 的 `slug`：`kb-result-qoder-build-v5-1-0`（与平台后台记录一致）。
- **产出成品包时**：技能**名**（`name` / `slug` / 目录名）沿用同一命名规则，换平台只调结构、**改名不加后缀**（`-xxx` 之类一律禁止）；**zip 文件名不在此列** —— 它带版本后缀，是版本管理与多版本并存的必需。

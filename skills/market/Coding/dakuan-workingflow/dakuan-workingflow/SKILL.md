# Dakuan Workingflow

## Overview

一套"设计做透再写代码"的工作流，分两个阶段共用一个 doc 树：

- **阶段 A（第 1–9 步）**：从 0 建项目。前 7 步全部是设计产物并按约定目录落盘，第 8 步才写代码，第 9 步整体测试过关后得到基线 B0。
- **阶段 B（迭代轨道 I1–I5）**：在基线上持续改进。每轮只解决一个可验收的目标，并把改动回写到阶段 A 的产物。

用于个人自研项目——决策者唯一且通常就是使用者本人。

## 硬性规则

- **一次只推进一步 / 一轮**：阶段 A 上一步交付物落盘并被确认合格，才进入下一步；阶段 B 一轮的 I1–I5 全部落盘，才开下一轮。禁止跳步或直接进入编码。
- **交付物必须写进对应文件**，不是脑内共识。每步/每轮推进后自动保存到下方目录结构中的对应位置。
- **阶段 A 内不许敏捷化**：第 1–9 步内不要提议垂直切片、MVP 迭代、"先跑通一条链路再说"、"尽早拿用户反馈"。迭代只发生在阶段 B 的轨道上，形态由 I1–I5 定义。
- **上游错误必须回上游**：阶段 A 的第 8、9 步与阶段 B 的任意一轮，发现设计错误都改第 5/6/7 步产物并同步受影响的其它产物，不允许在代码里就地自造结构、悄悄偏离契约。
- **数据结构变更不许跨轮**：任何表、字段、约束变更，必须在同一轮完成迁移、存量回填与回滚路径，禁止"下轮再迁"。
- **不许留半成品**：一轮结束时不允许"只改后端没改前端""新逻辑上线旧逻辑未清理"的中间态；做不到就缩小本轮目标，不许把中间态当成交付。
- **L2 / L3 变更先商议**：按变更分级判定，L2、L3 必须先给替代方案与代价并由决策者拍板，L1 才可直接执行。
- **局部改动走轻量通道**：同时满足四条判据时不建迭代目录，见"轻量通道"。
- 讨论节奏：约 300 字短答、一次一个问题、从最基础概念讲起，扮演挑漏洞的评审者而非顺从的执行者。

## 项目目录结构

新建项目时按此结构建目录和文件（文件无扩展名，`项目名称` 三处都替换为真实项目名）。参考模板在 `E:\ProjectsFile\workspace\项目目录参考`，**只取结构，不要复制其中的示例内容**：

```
项目根/
├── prompt.md                          记录开发流程各阶段的提示词，按"## 主题"分节
├── doc/
│   ├── 0_draft/                       未通过的高保真原型草稿（每端一套串联的 .html + 资源文件）
│   ├── 1_PRD/
│   │   ├── 项目介绍                    项目简介 + 使用者介绍 + 最简使用流程
│   │   └── 编码细则/
│   │       ├── 技术栈                  项目技术栈 + 选型原因
│   │       ├── 前端编码细则
│   │       └── 后端编码细则
│   ├── 2_原型图/                       已通过的高保真原型：一套串联的 .html + 资源文件，必要时附同名截图 .png
│   ├── 3_各模块说明文档/
│   │   ├── 01_模块1/{模块1前端, 模块1后端}
│   │   ├── 02_模块2/{模块2前端, 模块2后端}
│   │   ├── sql                        数据库搭建原语（DDL）
│   │   ├── yml                        配置样例
│   │   └── 开发部署手册
│   └── 4_迭代/                         阶段 B：迭代产物
│       ├── 0_迭代总览                  迭代表 + 当前迭代指针 + 变更分级
│       ├── 1_债务台账                  跨轮记忆：债务点与处理状态
│       └── NN_迭代名称/
│           ├── 01_功能说明
│           ├── 02_涉及模块
│           ├── 03_改动指南
│           └── 04_验收记录
└── 项目名称/
    ├── 项目名称_backend                后端代码
    └── 项目名称_forward                前端代码
```

`prompt.md` 与每步/每轮的推进同步：每进入新阶段或新一轮，把实际使用的提示词追加为一个新的主题节。

## 阶段 A：9 步与过关判据

| # | 做什么 | 落盘位置 | 过关判据 |
|---|--------|----------|----------|
| 1 | 明确使用者 | `doc/1_PRD/项目介绍` 使用者介绍段 | 一句话能说清谁 + 什么场景 + 解决什么问题。使用者=决策者时，自我判定即视为成立 |
| 2 | 最简使用流程 | `doc/1_PRD/项目介绍` 流程段 | 编号步骤序列能走通、每步有明确产出；**必须同时写明"本版本不做什么"**，否则简洁流程会在编码期悄悄膨胀 |
| 3 | 实现该技术候选 | 候选清单挂在第 4 步文件顶部 | 只列候选，不下结论 |
| 4 | 敲定技术栈 | `doc/1_PRD/编码细则/技术栈` | 区分两类分别给结论：不可逆项（数据模型形态、部署形态、是否多端）需写选型原因；可替换项（框架、库）不纠结，选熟的 |
| 5 | 原型图先行 | 草稿进 `doc/0_draft/`，通过后入 `doc/2_原型图/`：构建一份完整的高保真的原型图，界面之间可实际跳转，弹窗与下拉在原型内就地展开；不为单个界面拆文件，必要时附同名截图 .png | 主流程每个界面都有 + **每个界面的空态**；界面之间的跳转闭环能走通。异常界面不单独设计，统一走提示层；兜底界面仅作为"访问到未开发路由"的占位 |
| 6 | 确定前后端模块与接口 | `doc/1_PRD/编码细则/{前端,后端}编码细则` 定分层与命名规范；`doc/3_各模块说明文档/0X_模块N/{模块N前端,模块N后端}` 定每个模块 | 三层齐备：① 数据类（前后端可直接引用的类型定义，不是文字描述）② 调用关系与状态归属（谁调谁、请求-响应还是流式、状态存在哪）③ 失败降级（提示之后界面回到哪一态、服务端残留由谁清理）。缺 ②③ 视为不合格 |
| 7 | 设计数据库实体 | `doc/3_各模块说明文档/sql`（DDL）+ `doc/3_各模块说明文档/yml`（配置） | 每个实体列出状态枚举；**每个有副作用的操作必须有中间态**（处理中/部分完成/待清理）+ 清理或重试规则。只画成功路径的实体设计不合格 |
| 8 | 分模块编码 | `项目名称/项目名称_backend`、`项目名称/项目名称_forward` | 严格按第 6 步契约实现；跨模块传的数据结构必须引用同一份类型定义，不得各写一份 |
| 9 | 整体测试 | 测试与部署步骤写入 `doc/3_各模块说明文档/开发部署手册` | 走完第 2 步那条流程 + 每个空态 + 每个有副作用操作的失败后状态 |

## 阶段 A · 第 7 步之后的纸面走查

进入第 8 步前必做一次，成本一笔、省掉编码期的三份返工：

拿第 2 步的流程逐节点，用第 6 步的数据类和第 7 步的 SQL 实体，手工填入真实样例值，并对每个节点回答：

1. 这个字段的数据从哪来？取不到时填什么？
2. 这一步失败，用户看到什么、界面回到哪一态？
3. 这一步做到一半失败，服务端留下什么？谁来清？
4. 这一步重试，会不会产生第二份结果？

任一条答不出，回第 6/7 步补，不要拖到编码。

## 阶段 B：迭代轨道

**进入条件**：阶段 A 第 9 步过关。把基线写入 `doc/4_迭代/0_迭代总览`（日期、提交号、测试结论），此后每轮编号 I1、I2……

| # | 做什么 | 落盘位置 | 过关判据 |
|---|--------|----------|----------|
| I1 | 立项 | `doc/4_迭代/0_迭代总览` 加一行 + `NN_迭代名称/01_功能说明` | 目标一句话可验收；范围必须含"本轮不进什么"；来源标明（债务 / 第 2 步"不做什么" / 新需求 / 缺陷） |
| I2 | 影响面与方案 | `02_涉及模块` | 逐项列出模块·文件·动作、每处为什么必须改、"不改清单"、变更级别、放弃的替代方案与代价；L2/L3 的待决策点已获决策者同意 |
| I3 | 改动指南 | `03_改动指南` | 步骤到函数级（位置 → 现状 → 目标 → 数据结构 → 影响面 → 验证）；含常量与真值表、迁移与回滚、测试点；禁止"适当/合理/视情况" |
| I4 | 执行与验收 | `04_验收记录` | DoD 五项全绿：功能验收 / 测试 / 迁移与回滚验证 / 文档回写 / 无半成品 |
| I5 | 回顾与回写 | `04_验收记录` + `1_债务台账` + 阶段 A 受影响产物 | 定量结果 + 不超过 2 条下轮改进已落盘；新增债务已登记；回写映射逐条完成 |

**变更分级**（L1 可直接执行；L2、L3 先商议）：

| 级别 | 含义 | 典型改动 | 要求 |
|---|---|---|---|
| L1 | 局部新增 | 加可空字段、加分支、加文件，行为局部可逆 | 按指南执行，验收后记录 |
| L2 | 结构影响 | 改对外契约、加迁移、改排序/快照/共享类型、跨模块搬职责 | 先给替代方案、代价、影响面、回滚方式，经决策者同意 |
| L3 | 破坏性 | 改表结构语义、改事务边界、拆模块、改接口路径或命名 | 单独立一轮迭代，先出 01/02 再决定是否继续，不并入当前轮 |

**轻量通道**：同时满足四条才可免建迭代目录——① 不触及数据库结构与存量数据；② 不触及对外契约与生成客户端；③ 不改变用户可见行为与界面；④ 不跨模块搬职责。免走通道仍要遵守编码细则、补必要测试、在中文提交说明里写清动机与影响面。任一条不满足即回到 I1。

## 两阶段呼应

| 阶段 A 产物 | 在迭代中的角色 | 回写义务 |
|---|---|---|
| 第 2 步"本版本不做什么" | 迭代候选池的初始条目 | 某项被纳入时移出该清单并注明轮次 |
| 第 2 步最简流程 | 每轮都要验证"这条流程仍走得通" | 流程真变了才改 |
| 第 5 步原型图 | 涉界面改动先改原型再改前端 | 同轮更新 `doc/2_原型图/` 对应端的串联原型与跳转关系 |
| 第 6 步模块文档 | 迭代"涉及模块"的唯一命名来源，不新造模块名 | 数据类、调用关系、失败降级变了必须回写 |
| 第 6 步前后端编码细则 | 迭代实现遵守同一份规范 | 新约定回写细则 |
| 第 7 步 DDL / 实体 | 数据结构变更的源头 | 同轮回写 `sql` + 数据字典 + ER |
| 第 3/4 步技术栈 | 新依赖先回技术栈 | 不可逆项写原因，可替换项记一行 |
| 第 9 步开发部署手册 | 运行与测试口径沿用 | 部署步骤变了不同步即未完成 |
| `prompt.md` | 每轮追加一个主题节 | 与 9 步同等对待 |

反向规则：迭代中若判定是"阶段 A 做错了"（不是缺功能而是设计本身错），走"回上游"——先改第 5/6/7 步产物再改代码；若属本版本范围外的新需求，进候选池排队，不许顺手塞进当前轮。

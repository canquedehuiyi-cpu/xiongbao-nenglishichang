## 填写示例（合成，非真实项目）

以下示例围绕“发布说明核对 Skill”。所有数据为合成，仅示范填写粒度。

- 使用者与使用场景：版本负责人在每次发版前核对 release notes 与 commit 列表
- 用户原话或真实请求：“输入为变更列表，输出要按新增、修复、兼容性风险归类，并附可追溯依据”
- 现在的处理方式与具体痛点：人工逐条比对，平均 40 分钟，漏项率高
- 期望输出及其使用方式：分三类的 Markdown，直接粘贴到发布页
- 成功标准（可观察）：10 条样例变更中，分类准确率 ≥ 9/10，每条结论附 commit 依据
- 失败代价：错误归类会误导用户升级决策，属中高代价，需人工复核
- 目标平台及版本：Qoder CN 桌面版，Skill 机制
- 用户明确要求的交付物：一个可安装的 Skill 目录

| 编号 | 输入/情境 | 合格输出或行为 | 不合格表现 | 来源（真实/假设） |
| --- | --- | --- | --- | --- |
| 1 | 含 “BREAKING CHANGE” 的变更列表 | 归入兼容性风险并引用该 commit | 归入新增 | 假设 |
| 2 | 一条既修 bug 又改接口的变更 | 拆为两类并说明依据 | 只归一类 | 假设 |
| 3 | 变更描述为空或无法判断 | 标为“待核实”，不猜测 | 编造分类 | 假设 |

- 交付形态及理由：Skill——需求是稳定的可复用判断规则，非一次性任务
- 应触发的请求：“核对这份发布说明”“按变更列表生成 release notes 分类”
- 不应触发的请求：“帮我写发布说明文案”（创作，非核对）
- 输入格式与数据来源：Markdown 变更列表，来自 git log
- 输出格式：三节 Markdown，每条含 commit 短哈希
- 可用工具与运行环境：Read、Bash（git log）
- 读写范围、外部副作用与授权边界：只读仓库，不写文件、不推送
- 停止、失败与人工接管条件：无法定位依据 commit 时停止并列明待核实项
- 时间、成本或资源限制：单次核对 ≤ 100 条变更
- 待确认的关键假设：“兼容性风险”以是否影响既有调用方为准
- 研究所需主题、关键词和权威来源：conventional commits、semver、release notes 规范
- 提交任务清单供用户确认的方式：对话内给出编号清单，等待明确“确认”

# 需求合理性评估 · 4 维度判定清单

> Phase A 用，**可选**——已确认要做的需求可跳过；新需求 / 业务方第一次提出 / 没把握的需求强烈建议走。

---

## 维度 1：真实时 vs 伪实时 ★

### 判定矩阵

| 业务场景 | 决策频次 | 是否真实时 | 选型建议 |
|---------|---------|-----------|---------|
| 反欺诈 / 风控 | 秒级 | ✅ 真实时 | 实时 |
| 实时大屏（领导汇报）| 分钟级 | ✅ 真实时 | 实时 |
| 客服外呼触达 | 分钟级 | ✅ 真实时 | 实时 |
| 实时推荐 / 千人千面 | 秒-分钟 | ✅ 真实时 | 实时 |
| 业务运营每日看板 | 日级 | ⚠️ 伪实时 | 优先建议离线 |
| 周报月报 | 周月级 | ❌ 伪实时 | 改离线 |
| 算法训练特征 | 看场景 | ⚠️ 多数伪实时 | 看是否需要在线推理 |
| 财务对账 | 日级以上 | ❌ 伪实时 | 改离线（精度要求 vs 实时性矛盾） |
| 数据科学家临时分析 | 看场景 | ⚠️ 多数伪实时 | 改离线 + 临时表 |

### 引导问句（按顺序问，每问一个等业务方回答再问下一个）
1. **业务方拿这个数据要做什么决策？** （要业务方描述具体动作，不是"看一下"）
2. **这个决策的频次是多少？** （秒 / 分钟 / 小时 / 日 / 周）
3. **如果数据延迟 1 小时业务方能不能忍？4 小时？1 天？** （找到容忍边界）
4. **当前是用什么方式做的？为什么这次要换成实时？** （理解切换 ROI）
5. **预算和资源支持充足吗？** （实时成本是离线的 5-10 倍）

### 反模式（严禁踩坑）

- ❌ 业务方说"我要实时数据"——不追问就开干
- ❌ 业务方说不清场景 → 工程师"猜"业务意图
- ❌ 因为"团队/老板说要做实时"就接 → 没有 ROI 评估
- ❌ 把一切都做成实时 → 资源浪费 + 维护负担
- ❌ 用实时方案做 T+1 业务 → 复杂度爆炸，性能反而不如离线

## 维度 2：SLA 严格度

### 评估表

| 维度 | 选项 |
|------|------|
| 端到端延迟可接受范围 | 秒 / < 1 分钟 / 1-5 分钟 / 5-30 分钟 / 小时 |
| 漏数据可接受比例 | 0（强一致）/ < 0.01% / < 0.1% / < 1% / 看情况 |
| 是否对外（外部客户/API）| 是 / 否 |
| 是否进入计费/财务 | 是 / 否 |
| 是否进入监管报送 | 是 / 否 |

### 严格度分级（决定后续技术选型）

- **S0 极严**：对外 + 计费 + 监管 之一 → 必须双链路（实时 + 离线对账）+ 7×24 on-call
- **S1 严**：内部核心决策 + 延迟 < 1 分钟 → 必须 DQC P0 告警 + 兜底机制
- **S2 中**：内部运营看板 + 延迟分钟级 → 常规配置
- **S3 宽**：内部探索性 / 数据科学家 → 简化配置可接受

### 反模式

- ❌ 严格 SLA 没双链路 → 实时挂了业务全停摆
- ❌ 宽松 SLA 配 P0 告警 → 告警疲劳
- ❌ 对外业务不做对账 → 客户发现数据不一致

## 维度 3：优先级评估

### 评估表

| 维度 | 选项 |
|------|------|
| 相对其他需求紧迫度 | 高 / 中 / 低 |
| 业务承诺时间节点 | 硬截止 / 软截止 / 无 |
| Block 其他需求 | 是 / 否 |
| 高层关注度 | 高 / 中 / 低 |

### 引导问句

1. 如果团队现在排期满了，这个需求可以推后多久？
2. 业务方承诺的上线时间是？是对外 / 对内 / 对高层 ？
3. 这个需求做完后，是否解锁后续 X 个需求？

### 决策建议

- **优先级高 + 硬截止 + 真实时** → 立项，资源优先
- **优先级中 + 软截止** → 排入正常迭代
- **优先级低 + 无截止 + 业务说不清** → 推后 / 不做

## 维度 4：历史数据回刷 ★（容易被忽略）

### 引导问句（必问）

1. **上线后如果发现历史数据需要重算（口径变更 / bug 修复 / 业务规则调整），怎么办？**
2. **业务方对历史回刷有时效要求吗？** （T+3 内必须刷完 / 可以慢慢刷 / 不需要回刷）
3. **回刷的数据源还在吗？** Kafka 通常只保留 7-30 天，超期就需要其他兜底
4. **回刷的频次预估？** （一年 N 次 / 月度 / 周度）

### 决策矩阵

| 回刷需求 | 数据源情况 | 选型建议 |
|---------|-----------|---------|
| 不需要回刷 | — | 纯实时即可 |
| 偶尔回刷（年 < 2 次）| Kafka 内 | 实时 + 临时离线脚本兜底 |
| 偶尔回刷 | Kafka 已过期 | 实时 + 同步落 ODS 表 |
| 频繁回刷（月 ≥ 1 次）| — | 实时 + 离线双链路 |
| 回刷诉求强烈（口径不稳定）| — | **考虑是否本就该做离线** |

### 反模式

- ❌ 不考虑回刷 → 上线 3 个月发现口径错，Kafka 数据已过期，无法回刷
- ❌ Kafka 过期问题不预先处理 → 业务来要"3 个月前数据"时抓瞎
- ❌ 频繁回刷却做纯实时 → 每次回刷都要手工拼凑 = 隐性维护成本

## 何时跳过 Phase A

- 业务方已明确说"已经评估过了，确认要做实时"
- 历史评审过的同类需求复用
- 用户主动说"跳过评估，直接整理口径"

→ 跳过时**至少口头确认**："我跳过 Phase A，直接进 Phase B 口径拆解，OK？"

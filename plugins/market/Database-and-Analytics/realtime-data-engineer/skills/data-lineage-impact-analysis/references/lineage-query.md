# 血缘查询策略

## 平台选择

读取 `QODERWORK.md` 的 `lineage_platform` 字段：
- 阿里云 DataWorks 血缘（首选）
- 自建血缘平台
- 兜底：通过 SQL 解析 + Git 全文搜索

## 查询深度

| 变更类型 | 推荐深度 | 原因 |
|---------|---------|------|
| 字段改名 | 2-3 层 | 字段级影响有限 |
| 字段类型改变 | 3-5 层 | 类型不兼容会 cascade |
| 表下线 | 5+ 层 | 必须看全 |
| 表拆分/合并 | 5+ 层 | 同上 |
| 新增字段 | 1 层（仅核对消费方）| 通常向后兼容 |

## 查询范围

必须包含：
- 直接消费的实时任务
- 直接消费的离线任务
- BI 报表 / 看板（DataV / QuickBI / 自建）
- API 服务（数据服务平台）
- 数据科学家的探索任务

## 时间窗

不要直接用全量历史血缘——拉血缘后**必须按"最近 N 天访问"过滤**：

| 业务关键度 | 访问窗口 |
|-----------|---------|
| 核心业务 | 最近 90 天 |
| 一般业务 | 最近 30 天 |
| 探索性任务 | 最近 7 天 |

超出时间窗仍在血缘中的下游，归 L3（通知即可，可能已废弃）。

## 兜底（血缘工具不可用时）

- Git 全文搜索：`grep -r "<表名>" /path/to/sql/repo`
- 平台 SQL 解析（DataWorks 提供）
- 联系平台团队人工拉取

**严禁**：凭记忆判断"应该没人用了"——这是事故源头。

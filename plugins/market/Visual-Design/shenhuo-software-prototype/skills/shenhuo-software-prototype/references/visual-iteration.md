# 页面图、版本与采用基线

## 先代表页，再扩展

1. 从需求页表选最能代表布局和组件的一页：手机常为主列表／首页，PC常为工作台。用户指定页面优先。双端各自选代表页，用户只要一端就只做一端。
2. 建项前确定张数和比例。默认1.5K，手机9:16、PC16:9或16:10；特定设备比例按实时能力核对。手机9:16对应的生成图像素不等于CSS视口390px，二者分别记录，不固定把图片像素作为HTML布局尺寸。
3. 每图一个正面单视口界面，清楚文字和真实UI布局；不要设备外壳、立体透视、多页拼版、连线、浏览器演示边框或页面外说明牌。长列表先画首屏，滚动内容在HTML补齐必要模拟项。
4. 提交需求，展示真实方案与报价。图片下载后用宿主实际图片预览呈现，提示用户针对布局、颜色、信息密度或具体组件提意见。不能只给文件路径就声称用户已看图。
5. 用户认可后把代表页作为参考制作其他主要页面，保持颜色、字体层级、导航、按钮和间距。每页仍有独立用途与状态，不机械复制内容。任务规格不同必须拆开。
6. 其余主要页完成后立即按 [设计稿总览](design-board.md) 把采用的代表页和各页最新图放进同一个HTML，标注页面名称，在预览区打开。聊天中逐张列图不能代替总览。整组确认前不进入DESIGN.md和功能性HTML。

用户明确要求整组时按其要求执行，不能强制增加代表页轮次。提案ready且没有追问就是本次整组方案完成；它不意味着用户已采用图片，也不需要再从方案中挑一页才报价。实际清单与原需求不一致时在扣费生图前解决差异；冻结任务不可改参数重放，需新任务时说明新提案成本并沿用真实用户指令。

## 修改路径（当前连接器合同）

没有 `revise_image` 等语义修改工具，不编造接口。针对用户要改的页：

- 查询原任务，领取对应已结算 `variant_id` 的结果并下载原图。
- 核对图确实是目标页面及版本，用 `create_upload` 上传为reference，`get_upload`确认资产ID与哈希。
- 向同一固定设计师创建新任务，附原始需求、目标页ID、素材角色和用户逐条真实修改意见，明确要保留的元素来自用户要求／既有采用基线。不要擅自把模糊反馈扩为全套重做。
- 仅改一页则本次只生成这一页；新任务按新报价确认，不声称从旧整组冻结清单中单独按页计费或免费重生成。
- 领取并下载新版，更新同一个总览HTML中对应的页面卡片，标明新版待确认，重新在预览区呈现。多页修改逐页更新成功结果，未改页保持；旧稿保留在版本记录中。新图未采用前，已采用的旧图仍是基线，不自动把最新版写入最终交付清单。

同一工作区外另存图片迭代记录与任务ID，原图不覆盖。建议命名 `mobile-home-r01.png`、`mobile-home-r02.png`；输出格式遵循真实回执，不把jpg改扩展名当png。

## 采用清单

交付根目录 `prototype.json` 只记录当前采用稿，候选历史放在兄弟工作目录，不进入ZIP。每页至少包括：

| 字段 | 内容 |
|---|---|
| id、terminal | 稳定页面ID；mobile或desktop |
| route、viewport | HTML入口路径及hash／目标CSS宽高 |
| reference.path、sha256 | 本地采用图路径及实际文件哈希 |
| reference.source | shenhuo或user |
| reference.variant_id | 神火图使用真实作品ID；用户提供图为空 |
| approval.status、note | confirmed以及用户明确采用的原话／上下文依据 |

只接受用户对具体页面／版本或明确整组的采用确认。单页采用用于积累基线；进入实现前须用户明确确认当前整组，批量确认可分别写同一真实依据，不要求多问每页一次。“继续改”“新图已生成”不是采用确认。用户指定从已确认全套图直接做HTML可作为整组采用依据，不重复索取批准。无需为视觉未变的代码修复重新确认图片。

本地已批准图缺少神火ID时标记user来源，不伪造作品ID。不读取到图片内容时不能提取可靠视觉规范；明确缺失的文件或查看能力，保留其余工作。

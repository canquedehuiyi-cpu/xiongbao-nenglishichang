# 需求简报与验收草案

将问题证据转成可讨论的需求材料，不替用户作上线承诺。可读取既有证据组，也可直接读取原始反馈后先建立必要证据索引。

## 工作流程

1. 确认用户要讨论的问题、使用者与现有约束，读取相应证据和明确决定。参考 [需求方法与实例](references/brief-method.md) 区分事实、方案、假设和决定。
2. 为需求分配或沿用 R01 等编号，说明目标用户在什么场景下遇到什么障碍；引用反馈编号，不将分析假设冒充客户原话。
3. 给出期望业务结果与候选方案，说明替代方案及取舍。把权限、版本、适用对象和明确不处理的范围写到会影响实施的地方；不要用完整模板掩盖关键事实缺失。
4. 用“给定前提—发生动作—可观察结果”写验收草案，覆盖正常、受限角色和失败或边界场景。未知字段、容量和时限标为待决定，不能编写看似精确的假标准。
5. 如需优先级，使用用户给的目标与依据提出建议；数据缺失时以定性理由和不确定性呈现，不凭空计算收益或分数。排期、负责人及最终采用标为用户决定。
6. 交付需求简报、验收草案、证据索引及待决策清单。保存 Markdown 到指定任务目录；工具不可用时提供完整正文。不自动开发或对外传达批准。

## 验证

每项验收条件对应需求或已确认约束，读者可区分现状与拟新增行为。不同证据相互冲突时展示冲突而非抹平；如关键决定缺失，标明草案受影响范围，先完成其余部分。

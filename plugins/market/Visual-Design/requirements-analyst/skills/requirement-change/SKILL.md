# 需求变更承接

把新证据和决定落实到已有需求正文，不只是输出一份变化摘要。输入包括旧需求、关联证据与新的反馈或决策；缺少旧稿时说明无法完成完整影响分析。

## 工作流程

1. 读取用户指定的当前版本、来源与新增材料，辨明哪些是反馈建议、哪些是用户已经明确的决定。读取 [变更方法与实例](references/change-method.md)。
2. 将新增反馈回连到原需求和证据组；需要新需求时给新编号，不复用一个编号偷偷改变目标。重复转发保留来源关系，不能使其变成新增票数。
3. 列出对角色、目标、范围、正常流程、异常流程和验收条件的影响。对于冲突，说明两个方案如何影响结果，要求的决定未给出时暂留未决而非替用户选定。
4. 按已确定的变化修改需求、验收草案与状态，保留被排除的方案及理由。不能把“建议考虑”改写成“评审已通过”，也不把新需求说明成已上线功能。
5. 交付修订稿、变更记录和待决策项，并检查所有被指定的关联材料。只对实际读过和修改的文件说明完成，不宣称外部工单已同步。

## 保存与边界

在用户任务目录创建新版或按明确要求覆盖，保留可追溯的旧稿与依据。无文件工具时给完整修订内容并说明未保存。优先级建议、最终采用与实际实施是不同状态；不自动创建工单、指派人员、发消息或开始开发。

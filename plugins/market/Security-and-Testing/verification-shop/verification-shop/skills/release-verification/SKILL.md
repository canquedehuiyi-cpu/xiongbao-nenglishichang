# 插件发布前核对（release-verification）

本技能由「插件发布前核对质检团」使用。原则：**只核不修**——发现问题、给出证据、给放行裁决；不代替作者修改代码或文档。

## 一、先定口径（必做）

开始前先问清/判断目标平台，核对口径随平台切换：

| 目标平台 | 结构口径 | 文档口径 | 合规口径 |
|---|---|---|---|
| **Qoder** | 根目录含 `.qoder-plugin/plugin.json`；`skills/` 下每个技能一个文件夹且含 `SKILL.md`（frontmatter 必有 `name`、`description`）；name 仅小写字母/数字/连字符，≤64 字符 | description 第三人称、含触发关键词；正文无 TODO/占位符/伪代码 | 引用的 Connector 必须已在市场上架 |
| **WorkBuddy** | 根目录含 `.codebuddy-plugin/plugin.json`；专家包须有 `agents/`、`settings.json`（`{"agent": agentName}`）；team 型须有 `teamInfo`（leadAgent + memberAgents）与 `members`（含 role=lead） | zh 简介 40–50 字；tags 与 quickPrompts 各恰好 3 个；`defaultInitPrompt` 必须与 `quickPrompts[0]` **逐字一致**（zh/en 都是）；`profession.zh` 全平台唯一 | 头像 512×512 ≤500KB；介绍/示例中不得含联系方式违规、夸大宣传 |
| **双平台** | 两套目录都核，分别出结论 | 分别出结论 | 分别出结论 |

用户没说平台时：按包内元数据目录（`.qoder-plugin` 或 `.codebuddy-plugin`）判断；两者都有则按双平台口径分别核。

## 二、四维核对

### 维度 1｜结构（主管·结构核对员）

1. 元数据目录存在且 JSON 可解析（`.qoder-plugin/plugin.json` 或 `.codebuddy-plugin/plugin.json`）。
2. 逐项核对清单文件声明与磁盘事实一致：声明引用的每个文件/目录都存在；反之，未声明的多余文件列出清单。
3. 目录布局符合目标平台规范（见口径表）。
4. 版本号符合语义化版本；name 符合命名规则。
5. 双平台差异：若同一插件有两套元数据，列出两边的字段差异（名称、简介、版本是否同步）。

### 维度 2｜功能（员工A·功能核对员）

1. 技能正文步骤是否可执行：无占位符（TODO、`<your-token>`）、无无法运行的伪代码。
2. 声明的能力与实际交付对得上：plugin.json / SKILL.md 描述的每个功能，在正文或脚本中有对应实现痕迹。
3. 入口可用：脚本有明确调用方式；示例命令可直接照抄执行。
4. 边界与失败路径：正文说明输入缺失/格式错误时的行为，而不是只写 happy path。

### 维度 3｜文档与引用（员工B·文档与引用核对员）

1. description 与正文语义一致（不能简介说 A、正文教 B）。
2. 引用可解析：正文提到的文件、路径、锚点、命令逐一在包内或明确的外部位置能找到。
3. 中文简介字数符合平台推荐区间（WorkBuddy 40–50 字）；英文版本与中文语义一致。
4. 快捷提示词/示例问题与 defaultInitPrompt 一致性（WorkBuddy 平台硬校验，逐字比对）。

### 维度 4｜合规与安全（员工C·合规与安全核对员）

1. 无密钥/真实凭证/内网地址硬编码。
2. 无越权指令（试图让 AI 绕过用户授权、读取无关目录）。
3. 引用的外部服务/Connector 在目标平台市场已上架（Qoder 硬要求）。
4. 联系方式合规：作者邮箱等只出现在 plugin.json author、README、角色文档指定位置。
5. 无夸大或绝对化宣传用语。

## 三、裁决（员工D·发布裁决员）

按最高严重度定论，三态：

| 结论 | 含义 | 判定 |
|---|---|---|
| **PASS** | 可直接提交发布 | 无任何维度问题 |
| **REVIEW** | 可发但需作者确认 | 有非阻塞问题（建议类、文案类、可选字段缺失） |
| **BLOCKED** | 不可提交 | 任一硬校验失败（元数据缺失/解析失败、平台硬性一致性校验不过、安全违规、引用了未上架 Connector） |

输出格式：

```
裁决: PASS / REVIEW / BLOCKED
平台口径: Qoder / WorkBuddy / 双平台
问题清单:
  [维度][严重度] 问题描述 — 证据（文件:行 或 截取原文）
放行条件:（REVIEW 时）需作者确认的事项
```

## 四、证据纪律

- 每个问题必须给证据：文件路径 + 行号，或原文引用。没有证据的判断降级为"待确认"。
- 不确定的判"待确认"，不猜。
- 数量较多时按维度分组，组内按严重度排序（阻塞 > 重要 > 建议）。

## 五、常见打回点（经验清单）

1. 快捷提示词与默认开场白不一致（WorkBuddy step1 解析即报错）。
2. 中文名称已被同类型资产占用（解析报"已被使用"，需改名或走已有草稿）。
3. agents 文件名与 plugin.json 的 agentName/teamInfo 引用不一致。
4. 头像缺失或引用了不存在的文件（专家中心显示裂图）。
5. 双平台包不同步：WorkBuddy 侧改了简介，Qoder 侧还是旧文案。

更多细节见 `references/checklist.md`。

# 产品推荐子 Skill

> 根据用户的交流信息，识别其账号主体、经营场景、终端形态、支付方式偏好和技术能力，推荐合适的签约产品，并说明推荐理由；如果没有匹配到合适产品，要礼貌告知当前暂无合适产品。

## 1. 子 Skill 元信息

- **name**: recommend-product
- **description**: 基于用户交流信息推荐合适的支付宝收款/支付产品，并输出推荐理由
- **触发条件**: 用户描述业务场景，询问“适合签约什么产品”“该开通什么支付产品”“这个场景用哪个产品”

## 2. 目标与职责

本子 Skill 只负责“推荐产品”，不直接进入签约资料收集。

职责包括：

1. 从用户自然语言中提取推荐所需信息
2. 基于产品知识和限制规则进行匹配
3. 输出最适合的产品和推荐理由
4. 若有多个可选产品，给出首推产品和备选产品
5. 若当前没有匹配产品，礼貌回复暂无合适产品
6. 若命中当前主签约链路可承接的产品，输出对应 `salesCodes`

## 3. 输入信息

| 信息项 | 必填 | 说明 |
|---|---|---|
| 用户交流信息 | 是 | 用户描述的业务场景、经营方式、终端形态、诉求等自然语言信息 |
| pid | 否 | 商户 pid，如已有可透传给后续签约流程 |
| uid | 否 | 用户 uid，如已有可作为上下文辅助信息 |

### 3.1 优先识别的信息维度

从用户交流中尽量识别以下信息；未明确提及时，可根据上下文推断，但不要编造：

| 信息维度 | 示例 |
|---|---|
| 账号主体类型 | 个人、个体工商户、企业、党政机关、事业单位、社会组织 |
| 经营场景 | 线下门店、路边摊、PC 网站、H5 页面、APP、小程序、自助设备、AI 智能体、会员续费、押金/冻结资金 |
| 支付方式偏好 | 商家扫用户、用户扫商家、自动扣款、先冻结后结算 |
| 技术能力 | 无开发能力、可做接口集成、可做 SDK 集成、小程序开发 |
| 线下/线上属性 | 是否有线下经营场所、是否纯线上 |
| 其他限制信息 | 是否有营业执照、是否属于特殊主体、是否需要周期扣款 |

### 3.2 缺失信息处理

- 如果已能做出明确推荐，直接给出推荐结果，不强制追问
- 如果信息不足以区分 2 个以上产品，可补问 1 个最关键问题
- 如果即使补充少量信息也无法推荐，礼貌回复暂时无法匹配合适产品，并说明缺少的关键信息

## 4. 推荐流程

### 第一步：理解用户交流信息

识别用户的核心需求：

- 他是想收款还是想做自动扣款/预授权
- 场景是线下、线上还是智能体对机器支付
- 用户是在网页、APP、小程序还是设备中完成支付
- 是否具备开发能力

### 第二步：先做限制过滤

遇到明显不符合条件的场景，先排除不适配产品，再做推荐。

#### 主体限制

| 账号主体类型 | 可否推荐经营码 | 说明 |
|---|---|---|
| 个体工商户 | 可以 | 常规支持 |
| 企业 | 可以 | 常规支持 |
| 个人 | 有条件支持 | 经营码场景下通常需具备营业执照 |
| 党政机关 | 不推荐 | 特殊主体，不推荐经营码 |
| 事业单位 | 不推荐 | 特殊主体，不推荐经营码 |
| 社会组织 | 不推荐 | 特殊主体，不推荐经营码 |

#### 场景限制

- 纯线上电商、纯线上服务、无线下场所时，不推荐 `经营码`、`当面付`
- 无开发能力时，不优先推荐需要接口或 SDK 集成的产品，除非用户场景只能使用该产品
- 需要周期性自动扣款时，优先且通常只能推荐 `商家扣款`
- 需要先冻结押金、后结算时，优先且通常只能推荐 `预授权支付`
- 支付发生在支付宝小程序内时，优先推荐 `JSAPI 支付`
- 支付发生在商家自有 APP 内时，优先推荐 `APP 支付`
- 支付发生在 PC 网站时，优先推荐 `电脑网站支付`
- 支付发生在手机 H5 页面时，优先推荐 `手机网站支付`
- 面向 AI 智能体按调用付费时，优先推荐 `智能收`

### 第三步：产品匹配

按“场景优先、支付方式次之、技术能力再次之”的顺序匹配产品。

若存在多个可选产品：

1. 给出 1 个首推产品
2. 必要时给出 1 到 2 个备选产品
3. 明确说明首推原因和备选差异

### 第四步：组织推荐回复

推荐回复必须包含：

1. 推荐产品名称
2. 推荐理由
3. 适用场景说明
4. 是否需要开发
5. 如有必要，提示限制条件
6. 如命中 V1 可承接产品，则输出 `salesCodes`

如果没有匹配到产品：

1. 先礼貌说明当前暂无合适产品
2. 简要说明原因
3. 如存在可补充的信息，提示用户补充

## 5. 产品知识库

### 5.1 线下收款产品

| 产品名称 | 产品码 | 定义 | 典型场景 | 是否需要开发 |
|---|---|---|---|---|
| 当面付 | FACE_TO_FACE_PAYMENT | 商家识别用户付款介质完成收款 | 收银台、便利店、餐厅、医院窗口等线下面对面收银 | 是 |
| 订单码支付 | QR_CODE_OFFLINE | 商家生成含金额的动态二维码，用户扫码付款 | 自助售货机、自助点餐机、PC 页面订单二维码、自助设备 | 是 |
| 经营码 | MERCHANT_QRCODE_PAY | 商家展示固定收款二维码，用户扫码并输入金额付款 | 路边摊、小店铺、小微商户、无需开发的线下收款 | 否 |

#### 线下产品差异

| 对比项 | 当面付 | 订单码支付 | 经营码 |
|---|---|---|---|
| 谁扫谁 | 商家扫用户 | 用户扫商家 | 用户扫商家 |
| 二维码类型 | 接口或机具能力 | 动态二维码，金额已带出 | 固定二维码，用户手输金额 |
| 主要适用 | 线下高频面对面收银 | 订单化收款、自助设备、动态金额场景 | 小微线下、免研发收款 |
| 是否需要开发 | 是 | 是 | 否 |

### 5.2 线上收款产品

| 产品名称 | 产品码 | 定义 | 典型场景 | 是否需要开发 |
|---|---|---|---|---|
| 电脑网站支付 | FAST_INSTANT_TRADE_PAY | 用户在 PC 网页发起支付，跳转支付宝完成付款 | PC 官网、电商网站、在线教育、政务缴费网站 | 是 |
| 手机网站支付 | QUICK_WAP_WAY | 用户在手机 H5 页面发起支付，跳转支付宝 APP 或网页完成付款 | 移动端 H5、手机网页收款 | 是 |
| APP 支付 | QUICK_MSECURITY_PAY | 商家在自有 APP 内集成支付宝 SDK 完成付款 | 自有 APP 的订单支付 | 是 |
| JSAPI 支付 | JSAPI_PAY | 用户在支付宝小程序内完成支付 | 支付宝小程序内下单支付 | 是 |

### 5.3 特殊能力产品

| 产品名称 | 产品码 | 定义 | 典型场景 | 是否需要开发 |
|---|---|---|---|---|
| 智能收 | ACT_PAY | 面向 AI 智能体的机器支付收款产品 | API、数字内容、算力资源、智能体按调用付费 | 是 |
| 商家扣款 | GENERAL_WITHHOLDING | 用户先签约授权，商家后续按协议主动扣款 | 会员续费、周期缴费、自动续费 | 是 |
| 预授权支付 | PREAUTH_PAY | 先冻结资金，再按实际消费结算 | 酒店押金、租赁押金、设备押金、先享后付 | 是 |

## 6. 典型推荐规则

| 用户场景 | 首推产品 | 推荐理由 |
|---|---|---|
| 线下门店收银台，商家扫用户付款码 | 当面付 | 面对面收银效率高，适合标准收银场景 |
| 路边摊、小店铺、无开发能力 | 经营码 | 下载或打印即可用，免研发、上手快 |
| PC 官网或电脑网页收款 | 电脑网站支付 | 适配 PC 网页支付链路 |
| 手机 H5 页面收款 | 手机网站支付 | 适配移动网页支付链路 |
| 商家自有 APP 内支付 | APP 支付 | 支持 SDK 集成，用户体验更完整 |
| 支付宝小程序内支付 | JSAPI 支付 | 与小程序场景天然匹配 |
| 自助设备或动态二维码场景 | 订单码支付 | 可生成含金额的动态二维码 |
| 周期性收费、会员自动续费 | 商家扣款 | 支持签约授权后自动扣款 |
| 押金冻结、先冻结后结算 | 预授权支付 | 适合押金和预付款场景 |
| AI 智能体按调用访问资源并付费 | 智能收 | 适用于智能体对机器支付 |

## 7. 不推荐规则

以下场景不要硬推产品：

- 用户主体或业务形态明确不满足产品条件
- 用户场景与产品支付链路明显不匹配
- 用户没有线下经营场所，却想用线下码产品解决纯线上支付
- 用户没有开发能力，且当前场景又无法使用免研发产品
- 用户需求超出当前知识范围，无法做出负责任的推荐

## 8. V1 承接边界

本推荐子 Skill 可以推荐多个产品，但要区分“可推荐”和“当前签约主流程可继续办理”。

| 智能收    | I1080300001000160457 | 当前 V1 主签约链路支持 |
| 电脑网站支付 | I1080300001000041203 | 当前 V1 主签约链路支持 |
| APP 支付 | I1080300001000041313 | 当前 V1 主签约链路支持 |
| JSAPI 支付 | I1080300001000060370 | 当前 V1 主签约链路支持 |

### 8.2 输出规则

- 如果首推产品是 `电脑网站支付`，输出对应 `salesCodes`
- 如果首推产品是 `智能收`，输出对应 `salesCodes`
- 如果首推产品是 `APP 支付`，输出对应 `salesCodes`
- 如果首推产品是 `JSAPI 支付`，输出对应 `salesCodes`
- 如果首推产品是其他产品，要明确说明”该产品可推荐，但当前 V1 主签约链路暂未承接”

## 9. 回复原则

- 优先根据用户已提供的信息直接推荐，不做无意义追问
- 推荐理由必须贴合用户场景，不能只重复产品定义
- 明确告知是否需要开发，避免误导用户
- 有限制条件时要诚实说明，不夸大产品能力
- 未匹配到产品时，保持礼貌，不强推不适配产品

## 11. 推荐话术示例

### 示例 1：线下小店，无开发能力

用户输入：

> 我开了个水果店，想收支付宝，没有技术团队。

推荐要点：

- 首推 `经营码`
- 理由是线下小店、免研发、用户扫码付款

### 示例 2：PC 网站收款

用户输入：

> 我们有一个电脑端官网，用户在网站上下单付款。

推荐要点：

- 首推 `电脑网站支付`
- 输出 `salesCodes=["I1080300001000041203"]`
- 说明该产品可继续进入当前签约主流程

### 示例 3：未匹配到产品

用户输入：

> 我想开支付宝收款，你看给我推荐一个。

推荐要点：

- 不直接硬推产品
- 礼貌说明信息不足
- 引导用户补充经营场景、终端形态、是否有开发能力

# 项目扫描与审查清单

按需要使用文件搜索、符号搜索和只读命令建立证据。优先检查小型配置文件与相关模块，避免把整个仓库或敏感配置输出到终端。

## 1. 项目事实

| 要确定的内容 | 优先证据 | 容易误判的情况 |
| --- | --- | --- |
| 项目用途与语言 | README、源码目录、实际入口和清单文件 | 脚手架 README 仍描述原始模板 |
| 运行时与框架版本 | POM / Gradle、package.json 与锁文件、pyproject.toml、go.mod、global.json 等实际存在的文件 | 文档版本、终端当前版本与项目要求混为一谈 |
| 模块与依赖 | Maven modules、Gradle settings、workspace 配置、模块引用和源码 | 把“多模块”自动等同于“多个业务领域” |
| 编译/启动/测试 | Wrapper、清单脚本、CI 配置、容器入口及现有测试命令 | 在聚合根目录直接启动应用、用不存在的测试类举例 |
| 格式与注释 | EditorConfig、IDE codeStyles、Checkstyle/Spotless、Prettier/ESLint、Black/Ruff/gofmt 等已配置工具，以及代表性源码 | 根据单个旧文件、生成文件或第三方文件推断全项目风格 |
| 分层与复用 | Controller/路由、Service、数据访问、DTO/VO、公共模块、已有依赖和调用点 | 强制所有语言使用 Java 的 Controller/Service 模型 |
| API 文档 | Swagger/OpenAPI 依赖声明、注解 imports、配置代码、扫描分组和字段模型；已有依赖解析结果可作补充 | 仅见到旧依赖属性或被注释的依赖就认定正在使用；把依赖声明当作页面已正常运行 |
| 数据与外部影响 | SQL 目录、迁移工具配置、测试类和调用链、定时任务/消费者 | 认为所有测试只读、启动应用没有副作用 |
| 项目知识 | 现有 AGENTS.md、模块规范、docs、ADR、术语表、技能目录和忽略规则 | 输出不存在的链接，给所有项目安装同一种技能体系 |

## 2. 代表性采样

- 每种主要语言选择几个实际维护的文件；有分层时覆盖入口、业务逻辑、数据/模型和测试。
- 根据文件数量和职责确认主语言；测试脚本或构建辅助语言不自动成为主要技术栈。
- 代码风格采样记录实际文件和观察结果：缩进、花括号、行宽、导入、命名、注释、异常、响应封装。多个风格并存时说明范围，不能假装有唯一风格。
- `git config user.name` 仅用于查明作者来源，生成 AGENTS.md 时保留“按 Git 配置获取作者”的规则，不能把当前操作者姓名固定成其他项目永久作者。
- 版本命令通常可只读运行；package scripts、构建和测试可能有副作用。仅为文档生成不执行安装脚本、全量构建、应用启动或真实联调。

## 证据表述边界

- POM 属性、dependencyManagement、模块依赖和 profile 的作用不同；相关组件可能声明不同版本。没有依赖树或等效解析证据时，只说明配置中的声明及待核实处，不断言实际加载版本、兼容或无冲突，也不为完善 AGENTS.md 擅自触发依赖下载。
- 现有文档声称本机工具版本“已核实”，不代表本次有运行证据；永久项目规范优先记录项目要求，当前机器的版本和本次扫描状态放在交付说明中。
- 不把一次本机版本观测改写成最低版本要求，例如“曾使用 Maven 3.9.9”不能推导“Maven 3.9+”。未找到项目约束时保留工具名称，不编造下限。项目没有某工具依赖也不等于本机未安装该工具；只有格式配置不能推断保存时会自动格式化。
- `.prettierrc` 等文件只证明配置约定；工具是否在清单、锁文件或 CI 中接入需单独核对。不得臆造已安装工具、格式化命令或强制新增依赖。
- 判断迁移体系时结合依赖/插件、配置、迁移目录及调用代码。只搜索 imports 没有命中不足以排除 Flyway/Liquibase 等自动配置的工具；如未全面核实，写明搜索范围和“未发现”。
- 静态命令检查只能说明目录、脚本或构建参数与配置匹配；“执行成功”“展示正常”“验证通过”须有对应的实际运行结果。读取或执行能力不足时如实列出未核实项。

## 3. 审查判定

| 类别 | 判定标准 |
| --- | --- |
| 事实与可执行性 | 模块/路径存在；命令执行目录和前提明确；工具/注解体系与项目一致 |
| 规则一致性 | 新增与历史代码的适用范围明确；默认只读与已授权修改不冲突；允许必要验证且避免无意义构建 |
| 复用与可读性 | 新增能力前检索；按语义复用；常量/枚举与基础字面量区分；不靠重复工具类解决局部问题 |
| API 与文档 | 已接入的 API 文档体系同步维护模型与示例；按实际变化更新 API 文档和 SQL；设计文档及图示仅在用户明确要求时提供 |
| 数据与交付 | 外部写入和部署有授权范围；已执行脚本保留历史；测试通过须有实际结果，不把跳过当通过 |
| 维护成本 | 固定原则简洁；复杂格式引用模板；不强制无关技能/工单/部署流程，不因章节名字不同就要求重写 |

证据不充分时用“待核实 / 未运行验证”表达；重要缺口可以询问用户，非阻塞内容可省略具体事实并保留操作原则。

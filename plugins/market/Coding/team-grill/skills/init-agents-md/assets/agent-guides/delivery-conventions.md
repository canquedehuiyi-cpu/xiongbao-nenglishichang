# 交付文档与归档规范

生成或更新正式交付资料时读取；接口契约或数据库发生变化时，仅维护对应资料，不强制凑齐整套文档。

## 交付文档归档

代码完成后，按实际变更留存用于前端联调的 API 文档和数据库增量 SQL。无既有目录约定时使用 `docs/releases/<类型>-<目标版本>/`，按文档类型分目录、按中文需求或任务名称命名。

| 类型 | 用途 | 目录示例 |
| --- | --- | --- |
| `feature` | 公共开发、正常功能需求 | `feature-v1.7.1` |
| `bugfix` | 常规 Bug 修复 | `bugfix-v1.7.1` |
| `hotfix` | 紧急 Bug 修复 | `hotfix-v1.7.1` |
| `temporary` | 临时功能、试验方案或临时交付 | `temporary-v1.7.2` |

```text
docs/releases/feature-v1.7.1/
├── README.md                              # 任务索引、交付状态及上线顺序
├── api/需求名称接口文档.md
└── sql/
    ├── 001_需求名称.sql
    └── rollback/001_需求名称回滚.sql
```

- 目标版本以用户指定或已确认的发布安排为准，不直接使用框架的 Maven 版本；分支名仅作为参考，不能确定类型或目标版本时先确认。分支重命名不要求文档跟随改名。
- 同类型、同版本的需求共用目录；同一需求在 API 和 SQL 中使用相同名称主体。必要时在名称前加任务编号区分重名需求。
- 已配置迁移工具时使用其目录和命名，版本资料链接唯一正式脚本，不复制第二份；普通增量 SQL 编号在该目录的 `sql/` 内统一分配，从 `001_` 开始，按实际执行顺序排列，不按需求各自重新编号。跨目录依赖写入 README；有可行回滚脚本时放入 `sql/rollback/`，沿用对应编号。
- 没有接口或数据库变化时，不创建对应空文件或目录；回滚不适用时说明替代恢复方案，不生成形式化回滚脚本。
- 向已有版本目录新增交付资料时更新其 README，记录目标版本、关联分支、任务与文档链接、SQL 执行顺序及依赖、配置或缓存操作、交付状态；首次创建版本目录时建立该索引。`temporary` 还需说明临时用途和后续处置。
- 已发布版本保留历史含义；已执行的 SQL 通过新增脚本修正，不覆盖旧脚本。SQL 每份只保留一处正式来源，其他文档使用相对链接引用。
- `.scratch/` 保留讨论、实施计划和调试草稿；将最终交付内容整理到上述目录。已有历史资料未经迁移授权不搬动；初始化 SQL 与版本增量 SQL 分开管理。

## 内容要求和模板

生成前读取对应模板，按本次代码、表结构和已确认需求填写；模板中的示例、占位符及使用说明不进入最终文档。参考文件中的业务规则、旧路径、环境数据和验收结论不能当作当前任务事实。

- **API 文档**：使用 [接口文档模板](../document-templates/接口文档模板.md)，面向前端联调。包括版本/分支/任务信息、接口总览、枚举字典、按调用端组织的接口详情、前端改造清单和上线依赖。详情写清 HTTP 方法、路径、参数位置与类型、必填性、请求及响应示例、错误码、权限、行为变化和兼容性；新增接口给出完整契约，变更接口可只列变化字段但须标明范围。
- **SQL 脚本**：使用 [SQL 脚本模板](../document-templates/SQL脚本模板.sql)，沿用用途注释、整齐的字段定义、中文表/字段 COMMENT 和显式索引。补充目标库类型/版本要求、执行前提、顺序、重复执行语义、影响范围及验证/回退方式；根据实际变更编写建表、改表或数据修正 SQL，不套用参考表的业务字段。
- **交付核对**：检查字段序列化类型、空值/默认值、时间格式、单位、错误码及示例一致性；核对 API/SQL 清单、实际文件、JSON 示例、Markdown 链接和代码块。实现、实际测试及部署结果分别表述。
- **可选设计资料**：仅在用户明确要求时使用 [设计文档模板](../document-templates/设计文档模板.md)，按问题需要裁剪内容和图示；不作为默认交付或验收要求。

# 接收需求并直接全托管

<!-- @author xiuyu.yi -->

1. 当前宿主按本包运行准备取得 CLI 的 READY 回执。必须声明 `auto-mode-flow-v1` 和 `auto-mode-reminder-v1` 并通过创建、只读观察、恢复和完成托管命令检查；保留实际 Node 和 CLI 路径，不在阶段切换时重复安装。
2. 当前宿主直接执行，按任务职责处理用户原话、附件和已有授权。沿本方法提交，不另做需求访谈，不创建宿主团队或模拟多个专家发言。
3. 使用当前任务的绝对输入路径，JSON 只含 `content` 或 `message`，附件用既有 `--file`。调用一次：

```text
superun-ai chat create --auto-mode --no-wait --input <需求JSON文件> --file <用户提供的本地附件>
```

没有附件时省略 `--file`；只有附件时也按原上传合同处理。不附加演示、跳过问卷、高级设计师参数或自行构造自动节点字段。

4. 在内部保存真实 sessionId、runId、messageId、replyMessageId，不向用户展示创建回执表。创建已接纳但状态暂未同步时只查询原项目；写入结果不确定时核对既有项目和原任务，不重复创建或领取试用。
5. 展示一次 entryNotice.estimate 原文：**预计耗时2至6小时，预计消耗200至800算力值（按产品复杂度浮动）**。本次服务端实际 billingMode 为 FREE_TRIAL 时追加 entryNotice.trial：**你是首次使用托管模式，本次托管过程不收取算力值，看到结果后满意才收费。** 缺少真实模式时先查询，不自行认定免费。这是预计区间，不是固定总价或付款金额授权；后续查询或等待窗口不重复展示启动说明。
创建成功回执还需展示一次 entryNotice.progressGuide.message，并将 superun.ai 链接到 entryNotice.progressGuide.url：**全托管已启动，你也可以前往 [superun.ai](https://superun.ai) 查看制作进度。** 同一次创建只展示一次；创建失败或结果尚未确认时不宣称已启动，接续观察不重复启动引导。

6. 后台观察同一次运行：

```text
superun-ai chat auto-mode wait <sessionId> --run-id <runId> --entry-message-id <创建回执replyMessageId> --timeout 45
```

优先执行创建回执的 WAIT_AUTO_MODE.command，保留其中真实的入口消息锚点；尚未取得 runId 时第一次等待可省略，取得后所有后续操作固定同一 run。按原后台句柄读取结果；本地窗口超时仍在运行时，在下一次 wait 加 `--cursor <上一次stdout.json绝对路径>`，复用本项目游标，避免重新播放全部历史。保存本次 scope 的 runId、起止时间和 entryMessageId，报告及历程读取沿用这些真实标识，不重新提交需求。
传入完整的上一次结果文件，保留 cursor.reminder 中的计时起点和已提醒次数。五分钟提醒由 CLI 按同一次托管累计时间产生，接续不重新计时；宿主不另设提醒计时器或为提醒额外查询。暂停、制作结束或退出后不再发送制作中提醒。

## 真实对话和进度

- `conversation_message` 展示本次真实业务正文；外层协议与执行元数据先按 [中文展示规则](presentation.md) 转换，不附消息 ID 或来源核对表。同一消息 ID 用于内部更新正文，不重复追加。保留“发现问题、处理、验证结果”的连续关系；不把自动推进消息冒充用户再次确认。
- `task_progress` 展示当前真实任务与状态，沿原 ID 更新；没有变化时不刷屏，不编百分比和预计完成时间。
- `task_reminder` 原样展示 data.message，并将 superun.ai 链接到 data.url；同一 data.id 去重，不同 ID 即使文案相同也展示，不受普通进度无变化的过滤影响。当前宿主直接向用户展示。提醒后继续原观察，不把提醒当成完成或新的业务授权。
- 当前宿主按产品、设计、开发、QA 和运营职责解读本次真实结果，只保留一个观察任务。专业判断来自本次 CLI 结果，不模拟成员讨论或虚构协作记录。
- 出现真实预览时按宿主页面工具交付完整 URL 和全部端入口；不能以工具日志代替用户侧展示。
- 预览只从本次已有状态和交付结果读取；暂未就绪就继续观察，不调用 `chat demo`、`chat develop` 或风格生成/选择命令来寻找、补出链接。它们属于普通创作动作，不能当作只读查询。
- 仍在全托管时不调用普通 `chat wait` 或向主线发“继续下一步、开始研发、选择方案、批准规划、全选功能、扫描、发布”。云端引擎已经负责这些动作。
- 优先复用本次交接的状态、预览及报告；仅为补充必要事实时才读取其他现有查询。不为寻找预览附加 `--for-launch` 等写操作授权参数，不把查询返回的其他阶段动作当成新的用户授权。
- 用户要求调整本产品的表达、安装或工具使用方式时，在宿主处理，不作为应用研发需求发送给云端，不重建或重启远端制作。
- 用户在过程中咨询，由对应角色读取本次真实信息答复；无法确认的项目细节使用原项目工作台咨询。咨询不等于新研发，不借咨询中断或改写自动主线。

## 暂停与恢复

收到 MANAGED_PAUSED 后按 [中文展示规则](presentation.md) 说明真实暂停原因与可行处理方式，并用原生选择提供 **继续全托管**。用户处理并选择后调用：

```text
superun-ai chat auto-mode retry <sessionId> --run-id <runId>
```

恢复已接纳后继续原 run 的 wait。恢复失败展示实际原因；不能说调用已接纳就证明整次已完成。停止本地等待不代表取消远端业务。本地超时而服务端仍运行时不当作暂停，不调用 retry。

整次 DONE、交付文档同步后按 completion.md 展示。仅一轮结束、某个成员完成、命令退出码 0、预览可打开，都不代表整次全托管完成。

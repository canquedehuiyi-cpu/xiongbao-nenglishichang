## 先确认项目分工

本技能执行主入口交接的 sxq-cli 任务。新建或继续应用的完整请求，先读取 [superun 主入口](../superun-creation/SKILL.md)，完成项目定位与执行模式处理，再执行本次分工。已有主入口上下文时沿用，不重开项目。

云端新项目取得首次规划/功能清单时，先在正文展示清单并回到主入口处理开发模式；在主入口完成这一步之前，不弹功能勾选控件、不提交 SELECT。默认云端模式允许此前的需求与样式流程，不等于用户已选择继续云端研发。

样式、预览、发布的链接先按 [正文展示方法](../superun-creation/references/host-tools.md) 写入助手回复，之后再调用问答工具。

# sxq 本地开发

当前客户端直接负责需求分析、设计、编码与检查；sxq 负责项目同步和云资源操作。开发不消耗 superun AI 生成 token，客户端模型费用和云资源费用另计。不要调用云端生成来代做本地工作。

## 接管已有项目

用户已要求开发当前项目并明确选择本地模式时，直接完成关联、拉取、按项目配置准备依赖、启动本地 dev 并展示预览，再回复接管结果。首次接管先展示已选样式的现有实现，不自动开始新增功能或改写页面；云端推送、迁移、预览构建和上线仍按各自授权执行。

1. 继承原项目标识、用户需求与已答内容、所选风格、superun 返回的功能清单、当前任务及成果标准。确认原写命令已经返回；`NEEDS_INPUT` / `FEATURE_SELECTION` 等待用户选功能不是仍在运行的云端写操作。也不能仅凭 `development.started=true` 就认定功能代码正在生成。
2. 样式选择已提交并返回功能清单时，按现有证据继续本地接管。sxq link 的阶段与权限检查以其真实回执为准，不要求云端 CLI 额外返回数字阶段“2”。不提交云端功能选择来解锁关联。
3. 读取 [CLI 操作手册](references/commands.md)，核对当前可执行的 `sxq --version`；具体参数不清楚才读该命令 `--help`。CLI 缺失或不兼容时报告环境缺口，由宿主环境层准备，保留本次接管任务。配置查询使用 `sxq config list` 或 `sxq config get <key>`。
4. 选定用户可访问的源码目录：已有同项目绑定则复用；首次接管使用当前工作区内的空目录/明确源码子目录。目录不存在则创建空目录，不先写 package.json、框架配置或脚手架；不使用 kit 安装目录，也不覆盖其他项目绑定。保留宿主项目记忆所在目录和源码目录的关系。
5. 检查 `.sxq/config.json` 的项目绑定。未绑定时，在选定源码目录执行 `sxq link <原 sessionId>`，成功后立即 `sxq pull`；已经绑定同项目则直接按手册拉取。先取得真实源码，再读取 README、项目规范、需求材料、依赖锁文件和已有实现，沿用现有技术栈。
6. 按 README、package.json 的 scripts、packageManager 和锁文件准备项目依赖，沿用项目的 dev 启动方式。不把功能勾选、技术栈选择或新增需求文档作为启动前置条件。
7. 用宿主后台执行能力启动 dev；已有同项目服务则核对并复用。读取启动日志中的实际地址和端口，检查页面响应；服务应保持运行，不等待 dev 退出才交付。这里是本地开发服务器，`sxq preview` 更新云端预览环境，不能替代本地 dev。
8. 按 [宿主工具](references/host-tools.md) 展示真实本地地址，再回复源码目录、预览地址和当前状态，并保留启动命令、进程/任务句柄及就绪证据。关联、拉取或启动失败时说明阻塞点，不报接管完成。后续开发沿用同一项目和服务，按用户目标继续。
9. 接管完成后对用户说明控制权已经转交：superun 已经把 <项目名> 交给 Qoder 处理，<项目名> 现在由 Qoder 控制。同时提醒：本地模式不再使用这个项目在 superun 里的上下文、记忆和任务规划（不是 Qoder 缺少这些能力），适合做小范围的修改。

## 前置失败与恢复

- 真实命令提示未登录/凭证过期：执行 `sxq login` 发起浏览器登录，让用户完成浏览器中的授权；保留登录进程和同一任务、源码目录。以 CLI 成功回执确认登录，从关联/拉取继续，不重复模式选择、功能问卷或环境检查全流程。不能根据猜测的凭证目录不存在、旧记忆说“sxq 未安装”等信息推断当前登录状态。
- 真实 link 回执拒绝阶段或权限：说明实际缺口，保留原项目；不能改成“先离线从零写”或自动切回云端收费生成。登录是接管条件，不提供用新脚手架绕过关联的替代路线。
- 拉取失败或有冲突：先核对现有文件与来源，按手册保留用户修改并处理，不把失败说成已取得代码。不能为继续开发直接把已有源码目录清空。

## 执行与交付

- 需求已有答案则复用，设计和实现以当前项目技术栈为准；遵循用户项目的检查和测试要求。
- 同一项目的推送、迁移、预览、部署由一个执行者串行完成，完整审阅新增/修改/删除清单，已有授权持续有效。模式选择本身不授权这些远端动作。
- 本地检查、预览可用和正式上线分开报告；`sxq deploy` 打开确认页不代表发布成功。已授权部署后，通过真实外部入口核对本次变更。
- 插件私有技能通过 sxq 当前命令获取，按返回路径读取；不编辑 CLI 生成的技能文件，不把缺失能力悄悄转成云端生成操作。
- 模式选择和记忆由组合入口负责；保留真实项目、目录、在途状态和成果，不重复询问模式。



需要提问、展示或长命令时读取 [宿主工具](references/host-tools.md)。保留 sxq 的实际文本、stdout/stderr 和退出状态，不使用云端 CLI 的 JSON 包装脚本或等待协议。
